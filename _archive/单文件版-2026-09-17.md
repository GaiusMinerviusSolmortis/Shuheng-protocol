## 0. 原始表述（先原样记下，别丢）

> 我在想一个新的 harness 框架，这是在经历了无数的离散开发之后想到的：
> 将一切，包括提示词、人格、工具、技能等等，都注册成为**实例**，
> 这样就能在一个框架内造出通用的东西，并且**无视技术栈**。
>
> 比如那个网安相关的东西（pentagi），就可以把知识库和工具等等注册成为一个
> 后台运行的小服务，通过某种方式托付给一个智能体，智能体在提示词中了解到
> 自己有这些工具，然后进行调用 —— 有点类似于 MCP？
> 但是我希望它更像是一个**响应式的 tool**，然后规定一套**消息流**，
> 这样画 GUI 的时候实际上只是接收智能体和各种工具的 IO。
>
> 大概是这样：
> - **智能体**：带有基本信息，可以选择模型和人设之类的，还需要动态拼接提示词
> - **工具**：有自己的唯一 ID 和参数表，还要通过识别码之类的手段对智能体的请求鉴权，然后返回调用的结果
> - **记忆系统**
> - **工作区**

### 0.1 补充表述（2026-09-13 第二轮）

> 我是想基于过往的成果和开发经验造出**新的** harness。
> 我细品了一下，好像其实就是 MCP？但我的设想是「**万物服务**」：
> 被允许使用的工具和知识，在**实例阶段动态注入**目标智能体。
>
> 出于避免爆掉上下文的考量，不能全量注入。应该是：比如把一个网安相关的东西

> 以及**该如何去获取这个工具的相关知识** —— 有点像用命令行时面对一个不熟的工具，
> 打出工具名加 `--help`。
>
> 然后程序开始运行时有一个**中控**，负责动态拉起这些工具的服务进程，
> 并在 GUI 上显示出来方便管理。

## 1. 一句话定位

一个「一切皆实例」的通用 agent harness：
把提示词、人格、工具、技能、记忆、工作区全部注册成**可寻址的实例**，
用一套统一消息流让它们协作；**GUI 只是这条消息流的投影**。

工具与服务不预先绑定到某个智能体，而是**运行时按需拉起、按绑定注入** ——
「万物服务」+ 一个中控（§6）。智能体只知道"我有什么、怎么问"，
不知道"这个工具内部是什么技术栈"。

「无视技术栈」是结果，不是目标 —— 因为工具是独立服务，
它内部是 Rust / Go / Python / 一个 Docker 容器都不重要，
框架只认它暴露的消息接口。

「通用」也不是靠一套万能代码，而是靠**换绑定不换代码**（§2.3）。

## 2. 核心命题：一切皆实例

### 2.1 先分清两层：类（kind）与实例（instance）

这是最容易糊掉的地方，糊掉整个架构就散了。

| | kind（类） | instance（实例） |
|---|---|---|
| 谁定义 | 代码注册 | 运行时创建 |
| 举例 | 「shell 执行工具」这个能力 | 「在这台机器上、以这个工作区为根的那个 shell 服务」 |
| 生命周期 | 随框架版本 | 随用户/会话，可创建、持久化、销毁 |
| 变的是 | 能力边界 | 配置、权限、状态、部署位置 |

**为什么要分开**：`deepseek-harness` 的 "everything is a plugin" 是**代码期**扩展 ——
插件在构建/启动时接进来，改的是框架本身能做什么。
你想要的「注册成实例」是**运行期**实体 —— 不改框架，只是新增一个可被寻址的东西。

两者不冲突，是两层：kind 由插件代码提供，instance 由运行时装配。
分开之后，「无视技术栈」这句话才成立 —— 技术栈差异被吃在 kind 的实现里，
实例只是配置 + 端点 + 权限。

### 2.2 实例的公共属性（草案）

任何注册进框架的东西，至少要有：

- `id` —— 稳定、唯一、可被人引用（也就能被提示词引用、被日志追踪、被权限表引用）
- `kind` —— 它是什么类别
- `lifecycle` —— 常驻 / 按会话 / 按调用；谁负责启动和回收
- `capabilities` —— 它能做什么（**不是它是什么**，见第 6 节）
- `endpoint / 消息入口` —— 框架怎么跟它说话
- `state` —— 它有没有状态；有状态的话存在哪、怎么恢复
- `观测` —— 它的 IO 是否进统一消息流（**这条决定 GUI 能不能只做投影**）

### 2.3 绑定（binding）：实例之间那条授权关系

「被允许使用的工具和知识，在实例阶段动态注入目标智能体」——
这句话里藏着一个独立对象。它既不是智能体，也不是工具，
而是**两者之间的一条关系**。必须独立出来，否则它会退化成智能体上的一个字段列表。

```
binding = {
  agent_instance,       // 谁
  resource_instance,    // 能碰什么
  capability,           // 允许做什么（§7）
  scope,                // 作用范围（哪个工作区、哪些路径）
  expiry,               // 何时失效
  injection_policy,     // 怎么进提示词：只报名片 / 附手册 / 全量（§5.3）
}
```

为什么必须独立：

- 同一个工具可以绑给多个智能体，各自权限不同；
- 同一个智能体可以**换绑**工具集 —— **这就是「通用」的来源**：
  一个框架造出不同角色，靠的是换绑定，不是换代码；
- 解绑要能撤销（常驻服务尤其）；
- 审计要看的是绑定变更历史，不是某次调用的快照。

绑定是**中控签发的**（§6），也是能力制（§7）落地的位置。

| 类别 | 实例是什么 | 有状态？ | 需要常驻？ |
|---|---|---|---|
| 智能体 | 一个可被唤醒的执行主体 | 有（会话/上下文） | 是 |
| 工具 | 能被调用的能力端点 | 看层次（见第 5 节） | 看层次 |

| 人格 | 一组提示词 + 模型参数 + 行为约束的打包 | 版本化 | 否 |

| 工作区 | 文件根 + 配置 + 快照 | 有 | 是 |

这张表本身就是框架的边界声明 —— **没进这张表的东西，框架不管**。

## 4. 消息流：整个框架的宪法

这是最该先定、也最该只定一次的东西。GUI 能不能只做投影、工具能不能是异种语言、
权限能不能落地，全压在它身上。

### 4.1 信封（envelope）要有什么

- `msg_id` —— 消息自身唯一
- `ts` —— 时间
- `from` / `to` —— 实例 ID（`to` 可以是广播或一个订阅主题）
- `type` —— 消息种类（下节）
- `corr_id` —— 因果/关联 ID：把「一次请求 → 若干分片 → 最终结果」串成一条链
- `session_id` —— 会话范围
- `payload` —— 种类相关的载荷

### 4.2 消息种类（草案）

| 种类 | 方向 | 说明 |
|---|---|---|
| `request` | 调用方 → 被调方 | 发起一次操作 |
| `chunk` | 被调方 → 调用方 | 流式分片（进度、部分结果） |
| `result` | 被调方 → 调用方 | 终态结果（成功/失败同构，错误是结果的一种） |
| `cancel` | 调用方 → 被调方 | 中止（**必须第一天就有**，后补极痛） |
| `event` | 任意 → 订阅方 | 主动通知，不需要被请求 |
| `presence` | 实例 → 框架 | 上线/下线/健康状态 |

### 4.3 待定的硬问题

- 一次工具调用与一条 `corr_id` 是一对一还是一对多？
- 同一实例能不能并发处理多个 `corr_id`？并发上限谁定？
- `cancel` 是尽力而为还是必须确认？（影响工具实现难度）
- 消息流的持久化粒度：全部落盘还是只落 UI 关心的？

## 5. 工具：从「函数调用」到「常驻服务」

### 5.1 三个层次

你说「像 MCP，但更像响应式的 tool」。这个差别可以拆成三层，
**先选定你要到哪一层，是这份设计里最关键的岔路口**：

| 层次 | 形态 | 典型实现 | 需要什么 |
|---|---|---|---|
| **L1 无状态函数** | 调用 → 返回，调完即忘 | MCP tools、OpenAI function calling | 只要路由 |
| **L2 有状态服务** | 会话常驻，可查询中间状态、可续做 | 一个后台小服务（你说的 pentagi 那种） | 加实例生命周期管理 |
| **L3 可主动发起** | 工具自己产生 `event` 推给智能体，不等被问 | 无成熟参照 | 加事件总线 + 调度器；智能体的回合变成**可被打断**的 |

L1 你已经做过了（枢恒 / maskface / EasyTerminal 的工具全是）。
MCP 的天花板也在 L1（它只有 tools / resources / prompts 三种原语，都是被动的）。

### 5.2 「响应式」的真正含义只在 L3

**「响应式」的真正含义只在 L3**：工具是活的，它会说话。
代价是智能体循环不再由框架独占 —— 你要么引入一个调度器做仲裁，
要么规定"外部事件只能在回合边界注入"。这两个选择的复杂度差一个数量级。

建议：**协议先按 L3 设计（消息种类留全），实现先跑 L1/L2**。
这样以后上 L3 不用改协议，只加调度器。

### 5.3 渐进披露：`--help` 协议

你这条补充是对 MCP 最痛的问题的直接回答。MCP 把工具的**完整参数表常驻注入上下文**，
50 个工具就是 50 份 JSON Schema —— 工具越多越糟，而且是纯粹的死重。

你的设想拆开是两层：

| 层 | 内容 | 何时进上下文 | 成本 |
|---|---|---|---|
| **L0 名片** | 名字 + 一句话 + 何时该用 | 常驻，永远在 | 每个工具约 1 行 |
| **L1 手册** | 完整参数、示例、失败模式、注意事项 | **被调用时才拉**（`--help`） | 只用到的工具才付 |

成本公式从 `已注册工具数 × 手册` 变成 `已使用工具数 × 手册` ——
在工具多的场景是数量级差异。这是它的第一个好处，但不是最重要的。

**真正重要的是：手册可以是人话。** JSON Schema 只能表达结构；
`--help` 文本可以写"这个工具在 X 情况下会超时，先确认 Y"、
"在你的场景里应该这样用"。更进一步，手册可以**按任务/按智能体裁剪** ——
同一个工具，给不同智能体不同的 `--help`。这是 MCP 的静态 schema
结构性地做不到的事。

要防的坑：

1. **多一次往返。** 第一次调用前必须先拉手册，这是必付成本，接受它，不要试图绕过。
2. **手册质量决定一切。** 写差的 `--help` 比没有更糟 —— 模型会自己编。
   手册要写得像给新同事的交接，不是像自动生成的 API 文档。
3. **手册必须版本化，并跟着实例绑定走。** 否则"上个月能用"的行为无法复现。

先例（说明这条路被验证过）：Anthropic 的 Agent Skills 是同一套 ——
名字+描述常驻，正文按需加载，附带资源再按需；"code execution with MCP"
也主张把工具定义放文件系统按需读，而不是塞进 context。

### 5.4 缓存约束：为什么名册必须事件化

**问题精确化**：前缀缓存按**逐字节前缀**命中。
原方案里花名册在 system 段，加/减一个插件 → system 段变化 → 该点之后全部失效。

**你的解法（把动作变成事件）成立**，而且理由和枢恒Ⅵ 里"历史 append-only"
是同一条：**把会变的东西从「前缀」挪到「尾巴」**。追加一条消息不动它前面的
任何字节，已有缓存全部保住，只为新增那段付账。

但要注意三件事：

**1. system 段必须真的静态。** 别在里面放"你有 47 个工具"这种计数、
别放时间戳、别放会话 ID。

**2. 更大的坑在 `tools` 参数上。** 大多数 API 会把 `tools` 数组序列化进
prompt 的前部。也就是说 —— 只把花名册从文本里挪走**还不够**：
只要往 `tools` 数组里增删一项，前缀照样变。

> 这点要在目标 provider 上实测确认，但**按最坏情况设计**。

解法是：**让 `tools` 数组字节级恒定。** 两种形状，推荐第二种：

- 纯调度器：只暴露 `call_tool(name, args)` / `help(name, section?)` / `list_tools()`，
  三个（或更少）永不变化，其余工具全藏在后面。
- **冻结尾部 + 调度器（推荐）**：保留一小撮**永不变化**的核心工具走原生
  tool calling（`shell` / `read` / `write` / `apply_patch` 这类永远绑着的东西），
  把**一切动态的、按绑定注入的**东西交给那一个通用调度工具。

  原生 function calling 是模型被训练过的形式，全丢掉会变弱；
  但核心集固定不变，所以 `tools` 数组依然恒定，缓存不碎。

于是"有哪些工具、怎么用"完全走 append-only 消息 + 按需 `--help`。

**这一条同时解决了缓存和渐进披露两个问题 —— 它们是同一个决定的产物。**

**3. 撤销比安装危险。** 文本告知只是建议，模型仍可能去调一个已经被撤销的工具。
撤销必须在**中控/绑定层强制**（调用直接失败），文本通告只负责减少无效尝试。

> 原则：**提示词里的花名册是优化，`list_tools` 才是真相。**

### 5.5 help 的层次：man page 模型

大工具的 help 不能一次性全吐出来。按 man page 的规矩分三层：

| 调用 | 返回 | 量级 |
|---|---|---|
| `help <tool>` | 概览 + 章节目录 | 几十行 |
| `help <tool> <section>` | 该章节全文 | 按需 |
| `help --search <词>` | 跨工具定位 | 按需 |

好处不只是省 token：**help 变成了一棵可以走的树**。
智能体像在 lsp_symbol_demo 里走代码符号图那样去走工具的说明书 ——
"先看目录，发现第 3 章讲认证，再看第 3 章"。
这跟 §8 的语义简报是**同一个动作**，只是对象从代码换成了工具文档。

**报错即手册**（你在两个项目里都做过）在这里补三点：

1. 报错内容 = 错误说明 + 正确参数格式 + 一句"不确定就 `help <tool> <section>`"。
2. **别整份倾倒。** 只带相关章节，否则一次报错就是几千 token 的惩罚。
3. **help 结果是最该被 scrub 的东西。** 它会长期占着历史，
   但它是**可重新获取**的 —— 正好符合枢恒Ⅵ 里 scrub 的判据（保配对、清旧结果）。
   把 help 结果标成"可丢弃"，上下文治理就多了一整类可回收垃圾。

### 5.6 动态工具到底怎么"加载"：三档

先纠正一个隐含说法：**动态工具从来不被"加载"进 `tools` 数组。**
数组一旦冻结就再不变化。变的只有两样东西：
**绑定集**（中控侧）和 **名册事件**（会话侧，append-only）。

按"能不能从 shell 够到"分三档：

| 档 | 什么样的工具 | 注册成什么实例 | 调用路径 | 例子 |
|---|---|---|---|---|
| **A 本机 CLI** | 装在这台机器上的可执行文件 | **只要知识实例**（名字 + 手册），不需要端点 | 用 `shell` 直接跑 | rg / ffmpeg / nmap / kubectl |
| **B 远地或有状态服务** | shell 够不到，或有会话/生命周期 | 完整服务实例（端点 + 生命周期 + 绑定 + 能力） | `call_tool(name, args)` | pentagi 的 Docker 沙箱、知识库服务、浏览器会话、微信通道 |
| **C 组合能力** | 本以为要新工具，其实是编排 | 不需要注册 | `shell` + 一段脚本 | 批量处理 50 个文件、循环重试、条件分支 |

**A 档最被低估：它根本不需要调度器流量。**
要注入的不是"一个可调用端点"，而是"这台机器上有这么个东西，手册在这里"。
智能体拿到就用 shell 去跑。pentagi 那 20+ 个专业工具全落在 A 档。

**C 档是 shell 真正的价值所在：它把循环从模型的回合循环里搬进了程序。**
一次工具调用跑完 50 个文件，而不是 50 次往返。
这就是 "code execution with MCP" 被广泛采纳的原因。

**B 档才是调度器存在的理由** —— shell 之外的那个世界。

### 5.7 冻结核心集是 per-role，不是全局

前面说"核心集固定"，得补上限定：**固定的范围是「某个角色 / 智能体实例」，
不是整个框架。**

因为缓存本来就按会话前缀算，不同角色的前缀本来就不同：

- 编码角色：`shell` + `apply_patch` + `call_tool` + `list_tools`
- 纯服务编排角色（比如网安那个）：可能只要 `call_tool` + `list_tools`
- 非编码角色：`apply_patch` 对它毫无意义

规则：**一个角色的冻结核心集，在该角色生命周期内字节恒定。**
要加核心工具 → 发一个新版本的角色（角色 v2），开一条新缓存血脉。
这种变更很少，可以接受。

**由此引出一个必须直面的后果 —— 冻结核心集是一个安全决策。**

如果 `shell` 在核心集里且不受约束，那么能力系统对"一切 shell 够得着的东西"
就是装饰品：智能体根本不必走 `call_tool`，直接 shell 调 nmap 就行，
绑定表被完全绕过。所以：

> **shell 进核心集 ⇒ 能力边界必须落在沙箱 / execpolicy 层，而不是工具注册表里。**

这不是坏消息，是路线选择。codex-rs 就是这么做的（`execpolicy` +
`linux-sandbox` / `windows-sandbox-rs`：命令策略 + 平台沙箱），
你刚拉到 `D:\agent\refer\codex`，可以直接对着看。
EasyTerminal 的三级门控也是同一个位置上的东西 ——
只是它管"要不要问人"，管不了"不问也不许做"。

三条路，选一条或组合：

1. **shell 进沙箱**，沙箱策略本身就是能力边界；
2. **shell 走门控**，越界操作每次问人；
3. **shell 移出核心集**，一切走 `call_tool` —— 最安全，
   但丢掉 A 档和 C 档这两个最大的效率来源。

### 5.8 为什么 shell 不是死局：四个决定

前提先确认：**shell 必须留着。** 模型要靠它编译、跑脚本、拼装命令，
这是它最大的效率来源（§5.6 的 A 档和 C 档）。
要放弃的不是 shell，而是"**用文本策略管 shell**"这个手段。

分界线不是"有没有 shell"，而是 **shell 跑在什么里面**。

#### 决定一：默认拒绝 + 白名单减法

危险的集合无法枚举（无限）；**需要的集合可以枚举**（由任务决定，很小）。
所以策略方向必须是"默认拒绝 + 加白名单"，而不是"默认允许 + 加黑名单"。

EasyTerminal 里那张"危险命令识别（rm -rf / mkfs / reboot 等）"是后一个方向 ——
它在试图枚举无限的坏集合，永远补不完。

#### 决定二：策略写在「能枚举的维度」上，不写在命令上

不要去判断命令，去判断**面**。每个面都是个小集合：

| 面 | 策略形态 | 谁执行 |
|---|---|---|
| 文件系统 | 可读写哪些路径 | 内核 / 沙箱 |
| 网络 | 能不能出网、能到哪 | 内核 / 代理 |
| 可执行 | PATH 里有哪些程序 | 内核 / 文件权限 |
| 资源 | CPU / 内存 / 时间上限 | 内核 |
| 身份 | 以哪个 OS 用户跑 | 内核 |

**管理负担从"维护无穷规则"变成"维护五张小列表"**，而且这五张表都不靠匹配文本。

顺带说：**换 shell 样式（cmd / bash / powershell）不是安全控制。**
三者能碰到的东西一样，差别只在语法和 PATH 内容。
它是个 kind/instance 的配置项（§2.1），不是边界。

#### 决定三：身份 ID 的正确用法 —— 选世界，不查表

「调用 shell 时附上身份 ID，没分配到对应工具就拒绝」这个想法，
问题出在判定方式上：要判断"这条命令用的是哪个工具"，仍然得解析命令文本 ——
又回到 §5.4 那个无解的问题（`nmap` / `/usr/bin/nmap` / `env nmap` /
一个内部调用 nmap 的脚本 / 一段用别的语言重写了 nmap 功能的代码）。

同一个身份 ID，换个用法就成立：

> **身份 ID 不查"这条命令合不合法"，它选"这个进程看得见什么世界"。**

```
identity → { 文件系统视图, PATH 内容, 网络可达面, 凭证集, 资源限额 }
```

于是"智能体 A 能用 nmap、B 不能"这件事，**不需要解析任何命令**：
A 的世界里 nmap 存在，B 的世界里那个目录根本没挂进来。
边界在**进程创建那一刻**就定死了，命令随便怎么写都无所谓。

#### 决定四：权限提升走服务，不走 shell

这条一句话解决掉整个张力：

> **需要更多能力时，不是给它一个更大的 shell，而是注册一个服务。**

shell 的权限永远保持很小、所有智能体都差不多（就几档 profile）；
能力增长靠**加服务** —— 而每个服务是有界的、带类型的、可审计的、可单独绑定的。
这跟"万物服务"的框架完全一致。

推论：**无限的问题被设计掉了。** shell 侧的复杂度不随能力增长，
能力侧的增长落在服务上，而服务本来就是一对一定义的。

#### 「我真没招」的部分：不用自己发明

上面这五张表、这套策略语言，**已经有现成实现，而且你刚拉到本地**：

| codex-rs 里的 crate | 管什么 |
|---|---|
| `execpolicy` | 命令策略：允许 / 拒绝 / 询问 |
| `sandboxing` + `linux-sandbox` / `windows-sandbox-rs` | 平台沙箱 |
| `shell-escalation` | **沙箱默认 + 显式升级通道** —— "需要突破时怎么办"的答案 |
| `network-proxy` | 网络那个面 |
| `process-hardening` / `bwrap` | 进程加固 / bubblewrap |

更粗粒度但更成熟的：**容器**。一个智能体一个容器，
就是"给一个智能体一个世界"最成熟的实现 —— pentagi 用的正是它。

**代价要说清楚**：沙箱有真实的工程成本，而且会挡住正常工作流
（一次编译可能要写白名单外的目录）。所以正确的形状是
**默认在沙箱里 + 一条显式的升级路径**（走门控 / 走服务），
而不是"要么全放开、要么处处报错"。codex 的 `shell-escalation` 就是这个形状。

### 5.9 别家模型的格式：调度器恰好是那层抽象

各家格式确实不同：

| 提供方 | 工具声明 | 调用返回 | 结果回填 | 缓存 |
|---|---|---|---|---|
| OpenAI Chat Completions | `tools[].function{name,description,parameters}` | `tool_calls` | `role:"tool"` + `tool_call_id` | 自动，前缀匹配 |
| OpenAI Responses | 扁平 `tools[]{type:"function",name,...}`；**内置 `mcp` / `web_search` / `computer_use` 等类型** | `function_call` item | `function_call_output` item | 自动，前缀匹配 |
| Anthropic Messages | `tools[]{name,description,input_schema}` | `content[]` 中 `type:"tool_use"`（带 `id`） | `user` 消息中 `type:"tool_result"` + `tool_use_id` | **显式 `cache_control` 断点** |
| Gemini | `functionDeclarations` | `functionCall` part | `functionResponse` part | 隐式 |
| DeepSeek | OpenAI Chat Completions 兼容 | 同上 | 同上 | 自动，前缀匹配，记账 `prompt_cache_hit/miss` |
| 本地（Ollama / LM Studio / llama.cpp） | 多数兼容 OpenAI 形状 | 视实现 | 视实现 | 通常无 |

**这些差异不会消失，但调度器把它们从「每个工具 × 每个提供方」压成「每个提供方一次」。**

没有调度器时：40 个工具 × 4 家模型 ⇒ 40 个 schema 要在 4 种方言里都写对
（JSON Schema 的 strict / nullable / anyOf 支持度各家不同，失败模式也不同），
而且每加一个工具就要重验 4 遍。

有调度器时：**冻结核心集那 3~4 个工具的 schema，每家写一次，写完永不再动。**
其余动态工具的参数都以**普通 JSON 字符串**装进调度器的第一个参数里 ——
而"写一段 JSON"是所有这些模型共同具备的能力。

> 所以调度器不只是缓存优化，它同时是**格式抽象层**。
> 工具注册表从此不需要按提供方做适配。

代价与缓解：

- 文本内嵌调用通常不如原生 function calling 可靠 → 这正是核心集保留原生调用的理由；
- 调度器入口的 JSON 可能被模型写歪 → **报错即手册**（§5.5）在这里兜底，
  错误信息直接给出正确形状；
- 需要一层**适配器实例**把内部消息流翻译成各家形状。它本身也是一个实例
  （kind = provider adapter，capability = chat），与"一切皆实例"自洽。

一个顺带的观察：OpenAI Responses 已经有**原生 `mcp` 工具类型**，
意味着在 OpenAI 上你**可以**不自己写调度器。但那会丢掉生命周期、绑定与能力，
并且把设计锁死在单一提供方。建议仍自己实现，把原生 `mcp` 当作未来的映射优化。

## 6. 中控（Supervisor）

你描述的：程序启动时有一个中控，负责动态拉起这些工具的服务进程，
并在 GUI 上显示来管理。

**这个角色补上了 §18 的问题 2（谁拥有回合），而且补得很关键。**

| 职责 | 说明 |
|---|---|
| 生命周期 | 拉起 / 停止 / 重启 / 健康检查 / 回收孤儿进程 |
| 注册表 | 实例的登记、发现、状态同步 |
| 绑定 | 谁被授权用谁（§2.3），签发与撤销凭据 |
| 仲裁 | 工具要主动说话（L3）时，决定**何时**注入智能体的回合 |
| 审计 | 所有 IO 进统一消息流，可重放 |
| GUI | 消息流的一个视图（§9），**不是独立状态源** |

关键结论：**中控让"外部事件只在回合边界注入"成为一条可强制的规则。**
于是你既能要 L3 的响应式，又不必把智能体循环改造成并发调度器 ——
仲裁权集中在中控手里，风险可控。
这是我认为这版设计里最聪明的一步：用架构位置换掉了并发复杂度。

要防的坑：

- **中控是单点**：既是故障点，也是权力集中点。它崩溃不能带走全部工具
  —— 得想清楚"中控重启后，工具服务能否被重新接管"。
- **进程蔓延**：万物服务 = N 个进程。需要两条策略兜底 ——
  按域合并服务（一个域一个进程，而不是一个工具一个进程）、懒启动。
  你自己的 EasyTerminal README 里专门写了"无孤儿进程"，说明这个坑你被咬过。
- **资源分配与回收**：端口、句柄、工作目录、临时文件。

## 7. 鉴权：认身份，还是认能力？

你提到「通过识别码之类的手段对智能体的请求鉴权」。这里有个分岔：

- **身份制**：令牌证明"我是智能体 A"。工具需要维护一张"谁能做什么"的表。
- **能力制（capability）**：令牌证明"我被授权做 X，在 Y 范围内，到 Z 时间为止"。
  工具只校验手里的凭证够不够干这件事，不关心调用者是谁。

能力制的三个好处，正好对得上你的场景：
1. 工具是异种技术栈的独立服务时，**它不需要知道框架里的身份体系**，只要会验签；
2. 权限可以随工具有效期自然过期（L3 那种常驻服务尤其需要）；
3. 审计日志里记的是"做了什么"，不是"谁做的" —— 后者可以被伪造，前者配合签名不能。

**要提前防的坑：级联调用。**
如果工具 A 拿到凭证后能替智能体去调工具 B，权限就漏了。
要么禁止级联（工具的凭证不能转授），要么做**衰减**（转授时收窄范围）。

这一节跟你 EasyTerminal 的三级门控是同一条线：
门控管的是"要不要问人"，capability 管的是"问了也做不了不该做的事"。

**但要先读 §5.7：** 如果 `shell` 进了冻结核心集，
那么在沙箱/execpolicy 层补上边界之前，本节设计的能力制是可被绕过的。
能力边界的位置，比能力制的形式更重要。

## 9. GUI = 消息流的投影

你说"画 GUI 的时候实际上只是接收智能体和各种工具的 IO"。
这句话可以变成一个**可测的不变量**：

> **重放不变量**：只给一份消息日志，能不依赖任何外部状态重建出 UI 吗？

如果不能，说明渲染逻辑读了流外的状态 —— 那不是 GUI 的问题，是**协议不完整**。

这条给你的价值是：把"协议设计得好不好"从审美问题变成可验证问题。
写个重放器跑日志，UI 对得上就是对的。

## 10. 和 MCP 到底差在哪

你问"好像其实就是 MCP？"。逐条对比：

| 维度 | MCP | 这个设计 |
|---|---|---|
| 它本质上是什么 | 传输 + 发现协议 | 运行时 + 生命周期 + 协议 |
| 工具定义进上下文 | **全量常驻** | 两段式渐进披露（§5.3） |
| 工具形态 | 被动，请求/响应 | 常驻服务，可达 L3 主动发起 |
| 谁拉起工具 | 客户端 spawn stdio（传输细节，不可管理） | 中控统一管理，GUI 可见（§6） |
| 权限 | 无（只有整服务器粒度） | 能力制 + 绑定（§2.3、§7） |
| 知识/记忆 | `resources`（很弱） | 一等实例，可被绑定 |
| 编排与仲裁 | 无 | 中控 |
| 消息种类 | JSON-RPC 请求/响应 | 多类型信封，含 `event` / `cancel`（§4） |
| 工具间能否协作 | 无（每个 server 孤立） | 通过绑定与中控可组合 |

结论：**你保留了 MCP 的线协议形状（这是对的，生态在那里），
但在它上面加了三层它结构性地没有的东西 —— 生命周期、绑定与能力、上下文经济。**

所以不是"MCP 而已"，而是**"MCP 是其中一层"**。

更准确的血缘不是 MCP，是 **OS 微内核 + 能力系统**：
工具 = 驱动，智能体 = 进程，消息流 = IPC 边界，绑定 = capability 表，
中控 = init + 设备管理器。这个类比在遇到"谁能碰谁"、"服务挂了怎么办"、
"怎么发现服务"这类问题时，比 MCP 好用得多。

## 11. 工具服务规范（草案）

目标：**一套稳定字段，能把一个工具注册进中控，并自动渲染到 GUI 上。**
字段分四组，第四组最容易被漏、也最值钱。

### 11.1 四组字段

**A 身份（Identity）**

| 字段 | 说明 |
|---|---|
| `id` | 稳定唯一，可被提示词/日志/绑定表引用 |
| `version` | 工具自身版本 |
| `contract_version` | schema 形状版本（与工具版本解耦，见 11.3） |
| `title` | GUI 显示名 |
| `kind` | 实例类别 |
| `platforms` | 支持的平台（Windows / Linux / macOS / 远端） |

**B 发现（Discovery）—— 服务 §5.3 的渐进披露**

| 字段 | 说明 | 谁用 |
|---|---|---|
| `summary` | 一句话 | L0 名片，常驻上下文 |
| `when_to_use` | 什么时候该用它 | L0 名片 |
| `help_sections` | 章节目录 | L1，`help <tool>` |
| `help(topic)` | 取某一章 | L1，`help <tool> <section>` |
| `injection_policy` | 只报名片 / 附手册 / 全量 | 绑定（§2.3） |

**C 调用（Invocation）**

| 字段 | 说明 |
|---|---|
| `input_schema` | JSON Schema |
| `output_schema` | **闭合的**结果 schema（见 D） |
| `capabilities` | 需要的能力令牌（§7） |
| `annotations` | `readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint` |
| `lifecycle` | 常驻 / 按会话 / 按调用 |
| `idle_timeout` | 会话空闲回收 |
| `health` | 健康检查入口 |

`annotations` 这四个字段是从 MCP 的 `ToolAnnotations` 抄来的，Serena 也在用 ——
**它们让 GUI 能在不调用工具的前提下就知道该不该画成危险色**。

**D 事实（Result）—— 最值钱的一组**

见 11.2，这是从 cua 的 `ActionResult` 学来的，也是我认为整套规范里唯一
非抄不可的部分。

### 11.2 把「事实」和「意义」分开

一个动作返回什么？大多数框架返回 `{success: true}` —— 这是个坏字段，
因为它把两件事混成了一件：**执行器知不知道动作生效了**，和
**这件事对任务意味着什么**。

cua 的做法（`libs/cua-driver/docs/action-result-contract.md`）值得整段搬：

```json
{
  "effect": "confirmed",
  "route": "accessibility",
  "delivery": {"mode": "background"},
  "evidence": [{"kind": "value_readback"}]
}
```

| 字段 | 取值 |
|---|---|
| `effect` | `confirmed` / `partial` / `unverifiable` / `suspected_noop` / `refused` |
| `route` | `accessibility` / `synthetic_events` / `global_input` / `dom` / `trusted_input` |
| `delivery.mode` | `background` / `foreground` / `not_applicable` / `unknown` |
| `evidence[].kind` | `value_readback` / `window_change` |
| `escalation.target` | `pixel` / `foreground` / `page` / `session` |

四条硬规则，每条都能救命：

1. **`unverifiable` 既不等于成功，也不等于失败。** 拿到执行器的确认而拿不到
   可信读回，就是 `unverifiable` —— 截图变了、原生 API 返回了，
   都**不足以**升级成 `confirmed`。
2. **验证是独立的一次调用。** `verify_state` 返回
   `satisfied` / `unsatisfied` / `unknown`，而且明确规定：
   **`unknown` 永远不能被当成成功。**
3. **升级建议属于 harness，不属于驱动。** 驱动只返回
   `escalation: {target, reason}` 这种**建议**；要不要换路线、要不要提权，
   由中控决定（§6）。驱动不该自己重试。
4. **会话生命周期本身是一组标准工具。**
   `start_session` / `get_session` / `list_sessions` / `end_session`，
   外加**隐式会话**：普通调用不需要显式开，运行时按传输租约自己建一个，
   复用直到传输关闭、显式结束、或空闲超时（cua 是 5 分钟）。
   这就是 L2「常驻服务」（§5.1）的标准形状。

第 3 条尤其值得注意：**它和 §6 的中控职责是同一个决定的两种说法。**
驱动把 "我做不到，建议你换这条路" 作为**数据**返回，而不是自己乱试 ——
于是仲裁权完整地留在中控手里。

### 11.3 让规范不腐烂的机制

cua 那份 `contract/manifest.json`（123 KB）不是手写的，是**从 Rust 类型生成**的，
而且 CI 里跑三条校验：生成器可复现、与活的工具注册表**逐字段对齐**、
Python/Node 绑定能穿过真实 FFI 加载。文档里有一句很关键：

> 已发布的工具**从 contract 里解析能力令牌，而不是另查一张运行时表**。

也就是说：**规范是唯一真相，运行时从它派生。** 手写一份 spec、代码里再写一份 ——
两份一定会漂移。这一条比字段本身更重要。

### 11.4 能力声明：两种写法

- **Serena 式**：用类继承表达能力 —— `ToolMarkerCanEdit`、
  `ToolMarkerSymbolicRead`、`ToolMarkerSymbolicEdit`、`ToolMarkerBeta`、
  `ToolMarkerDoesNotRequireActiveProject`，然后派生
  `can_edit()` / `is_readonly()` / `is_symbolic()`。
- **MCP 式**：用注解字段 —— `readOnlyHint` / `destructiveHint` / `idempotentHint`。

**跨语言场景选后者。** 继承是语言内的机制，注解是数据 ——
而"无视技术栈"（§1）要求能力必须是数据。

顺带一个细节：Serena 在 `mcp.py` 里有个
`_sanitize_for_openai_tools(schema)`。说明**即使 schema 设计得再干净，
仍然要按提供方做一次清洗** —— 这与 §5.9 的判断一致，
而且再次说明适配层躲不掉，只能被压缩。

## 12. 表示层：GUI 与文字怎么响应

### 12.1 一个动作，一份表示，三个消费者

UFO 的做法值得直接抄：`ActionCommandInfo.to_representation()` 把一次动作
规范化成固定形状的文本 ——

```
[Action] click(control_name='保存', control_type='Button')
[Target] name=保存, automation_id=btnSave, class=Button
[Status] success
[Result] ...
```

关键在于**这一份表示同时喂三个消费者**：

| 消费者 | 用途 |
|---|---|
| GUI | 渲染成卡片 |
| 模型上下文 | 作为历史里的动作记录 |
| 审计日志 | 可重放的证据（§9 重放不变量） |

一份表示三个用途，意味着**三者永远不会说出互相矛盾的话**；
而且只要这份文本能重建 UI，重放不变量就成立。
如果 GUI 有自己的一套渲染逻辑、日志有另一套，两边迟早对不上。

### 12.2 模型输出要分两条通道

OpenAI CUA 示例的 `responses-loop.ts` 里有个容易被忽略的字段：
assistant message 的 `phase`，取值 `commentary` 或 `final_answer`。
它把模型的文本输出**分成两条通道**：

- **commentary** —— 过程解说："我先把表单填上再提交"；
- **final_answer** —— 最终答复。

两者在 UI 上去完全不同的位置：解说进过程流，最终答复进对话区。
**绝不能把解说混进最终答案** —— 这是很多 harness 做出来"读起来很乱"的根因。

对应到 §8 的动态提示词编译：出厂时就要在提示词里规定"哪类内容走哪条通道"，
而不是事后从一大段文本里猜。

### 12.3 事件契约

CUA 示例的事件形状可以直接当草案：

```ts
{ id, runId, sequence, type, level, message, detail?, createdAt }
```

- `type` 是**闭合枚举**（`run_started` / `function_call_requested` /
  `function_call_completed` / `screenshot_captured` / `run_progress` /
  `run_completed` / `run_failed` / `run_cancelled` …）
- `level` 是 `ok` / `pending` / `warn` / `error` —— 这正是 GUI 需要的颜色语义
- `sequence` 单调递增，保证顺序可重建
- 它的 `replayBundleSchema` 带 `version: 3` —— **重放包是版本化的**

这四条合起来，就是 §9 那个"重放不变量"的可用形状。

### 12.4 GUI 的粒度

从这四个项目看下来，GUI 只需要渲染三样东西：

| 粒度 | 数据来源 | 渲染 |
|---|---|---|
| **卡片** | 一次工具调用（含 11.2 的事实字段） | 可折叠、带颜色（危险色调来自 `annotations`） |
| **流** | `chunk` / `commentary` | 追加文本，不重排 |
| **状态** | `level` + `sequence` | 时间线 / 进度 |

cua 甚至维护了一份 `action-icon-catalog.md`（25 KB）——
**动作到图标的字典**。说明 GUI 需要一份"动作类型 → 视觉"的映射表，
而这份表应该是**从 11.1 的 `kind` + `annotations` 派生**的，不是手写的。

## 13. 窗口托管

### 13.1 「托管」有三种强度，代价差一个数量级

| 强度 | 做法 | 代价 | 可靠性 |
|---|---|---|---|
| **摆位托管** | `SetWindowPos` 把目标窗口摆到指定位置，`SetWinEventHook` 监听 `EVENT_OBJECT_LOCATIONCHANGE` 把它按回去，外框自己画 | 低 | 高，不改变所有权 |
| **镜像托管** | `Windows.Graphics.Capture` / Desktop Duplication 把窗口内容抓成纹理，渲染进自己的表面；输入用 `SendInput` 转发 | 中 | 高，对任何窗口都有效 |
| **真托管** | `SetParent(child, mine)` 把外部窗口变成自己的子窗口 | 高 | **低，会坏** |

摆位托管就是窗口管理器的路子（PowerToys FancyZones 那一类）——
**看起来像被托管了，但窗口其实没换过爹**，所以没有任何脆弱性。

镜像托管是远程桌面的模型：你看到的是一份实时的**副本**。
代价是真正的窗口还在原地，焦点和激活会打架；而且 DRM 保护的内容抓出来是黑的。

### 13.2 真托管会坏在哪里（清单）

- **DPI 感知不一致** → 托管后缩放错乱。经典坑，两边的 awareness context 必须一致。
- **UWP / WinUI / Store 应用**基本不能 reparent（活在 `ApplicationFrameHost` 里）。
- **自带合成/交换链的**（浏览器 GPU 合成、Electron、游戏）常常黑屏或卡死。
- **UIPI**：低完整性进程不能给高完整性窗口发消息，也不能 reparent 它。
  也就是**非管理员的智能体托管不了管理员的窗口** —— 这是内核级硬边界，
  和 §5.7 里 shell 面对的是同一道墙。
- **目标进程消息循环卡住时**，`SetParent` 会阻塞甚至死锁。
- 输入路由改变，很多应用会行为异常。

### 13.3 但很可能这个问题问错了

「把窗口托管给我」通常真正想要的是**控制权**，不是**像素**：

| 真正想要的 | 够用的做法 |
|---|---|
| 我看见它 | 镜像托管 |
| 我操作它 | UIA（UFO 路线）+ 合成输入 |
| 它跟着我的工作区开关 | 摆位托管 + `SetWinEventHook` + `ShowWindow` |
| **它真的住进我的窗口，共享我的布局和消息循环** | 只有这个需要真 reparent |

而最后那条恰好是所有诉求里最罕见的一个。
先问清楚"我要的是看见、操作、还是真的住进来"，能省掉一整个子系统的复杂度。

### 13.4 桌宠那一半反而简单（而且你已经在做）

创建自己的窗口是成熟技术：无边框 + `WS_EX_LAYERED`（逐像素透明）+
`WS_EX_TOPMOST`（置顶）+ `WS_EX_TOOLWINDOW`（不上任务栏）+
`WS_EX_TRANSPARENT`（点击穿透）；圆角用 DWM 的
`DWMWA_WINDOW_CORNER_PREFERENCE`。

你 maskface / EasyTerminal / WXBot 已经在做 egui 窗口了，
而 `D:\agent\refer\Python-island-imgui` 那个分支做的正是
**Win32 + D3D11 全屏透明叠加层** —— 那份代码可以直接参考。

### 13.5 接进框架：窗口也是实例

窗口天然满足 §2.2 的全部属性：

```
kind      = window
lifecycle = 自建 / 托管 / 镜像
capabilities = 能不能控、能控到什么程度（读？点击？注入文本？）
state     = 位置、可见性、焦点、所属进程
观测      = 它的窗口事件进消息流
```

**关键收益：如果窗口事件也进消息流（§9），重放不变量就从"对话可重建"
扩展到"桌面可重建"** —— 整个工作区的视觉状态可以从日志重放出来。

### 13.6 两个必须提前想的风险

**1. 能画桌面的智能体能冒充操作系统。**
一个能渲染任意窗口的 agent，可以画一个假的"确认"按钮骗你点。
所以：**同意与授权界面必须由中控绘制，并且在视觉上必须与 agent 内容不可混淆。**
这不是可选项，是这套能力能不能交出去的前提。

**2. 窗口控制是 shell 问题的 GUI 版。**
`SendInput` / `PostMessage` / `SetParent` 面对任意窗口时同样是无界能力，
内建边界只有 UIPI 一道。所以窗口控制必须走 §7 的能力制 + §5.8 的纪律，
**不能是"框架自带的免费权力"**。

### 13.7 托管 ≠ 操作通道：把 IDE 场景拆开

目标场景：「把 IDE 托管给一个智能体，它自己对着项目改代码」。

这里面其实是**四件可以独立决定的事**，绑在一起就会选错方案：

| 事 | 问什么 | 可选做法 |
|---|---|---|
| **视觉归属** | 它出现在哪 | 摆位托管 / 镜像进自己面板 / 真 reparent |
| **控制通道** | 我怎么操作它 | 插件 API / LSP / UIA / 合成输入 / 像素 |
| **观察通道** | 我怎么看它 | 截图 / 结构化控件树 / 状态查询 |
| **归因** | 我怎么知道谁做了什么 | 框架消息流 / 被控应用自己的日志 |

**「托管」只回答了第一件。** 把它当成"操作能力"是最容易犯的错。

控制通道是一条**阶梯**，每往下一级就少一分语义、多一分脆弱：

```
插件 API  ← 引用感知、原子、可归因        （serena 的 JetBrains 工具）
LSP       ← 语义级、可归因                （serena 的 symbol 工具）
UIA       ← 结构级、半可归因              （UFO 的主通道）
合成输入   ← 坐标级、难归因                （SendInput / PostMessage）
像素      ← 最脆、几乎不可归因             （截图 + 点击坐标）
```

**cua 的 `route` 字段（§11.2）记的就是"这次走了哪一级"** ——
它是"这条结果该被信任多少"的度量，也是这条阶梯的现成编码。

对 IDE 场景的结论不太客气：**改代码这件事，GUI 通道是这条阶梯的最差选择，
插件 API 是最好的选择。** Serena 的 `jetbrains_tools.py` 里有
`JetBrainsRenameTool` / `MoveTool` / `InlineSymbol` / `SafeDelete` ——
那才是"真的驱动 IDE"，而且它走插件 API，不是点击。

**推荐形状**：托管只负责"它住在我的工作区里"（摆位托管足够），
控制优先走插件 API / LSP，只有插件够不到的东西（运行配置、调试器面板、
插件专有界面）才降级到 GUI 通道 —— 而这些降级动作**恰好最需要人工确认**，
因为它们的归因最弱。

### 13.8 托管一个窗口 = 借用它的全部权限

这条得说透，因为它会让前面所有沙箱设计失效。

**被托管应用的写操作发生在它自己的进程里，不经过你的沙箱。**
IDE 能写这个用户能写的任何位置、能跑 task runner（等于任意命令）、
能装扩展、能读它配置里的 git 凭证和 token。

> **把 IDE 托管给智能体 ≈ 把用户的全部开发权限交给智能体。**

§5.8 那套"五个面 + 沙箱"在这里帮不上忙 —— 越权的不是智能体的 shell，
是**被托管的应用**。这是 confused deputy 的 GUI 版。

三条缓解，用的都是前面已经定过的同一套手法：

1. **限制被托管应用的作用域** —— IDE 只打开指定 workspace，禁用任务运行器。
2. **用独立 OS 用户跑被托管应用** —— 这正是 §5.8「身份 = 选世界」，换个战场再用一次。
3. **把它当成最高级权限，显式授予** —— 承认有些东西管不住，那就明确要一次授权。

第 3 条是诚实的底线：**如果一条能力无法被约束，正确的做法是让它变得显眼，
而不是假装它被管住了。**

### 13.9 为什么 GUI 里看不见鉴权路径

答案比"GUI 显示得不清楚"更根本：

> **GUI 是为「操作」设计的，不是为「归因」设计的。**
> 用户点一个按钮，界面告诉你结果，不告诉你权限。

于是有两层问题，一层可解，一层不可解。

**第一层（可解）**：鉴权信息必须由中控写进消息流，GUI 再从流里渲染。
具体做法是每次动作事件都带三个字段：
**用了哪个能力（capability）、由哪条绑定授权（binding）、是否经过人工确认（consent）**。
GUI 就能在卡片上画徽章（"由绑定 B-42 授权 · L2 自动执行"），日志也能审计。

**前提是动作经由你的框架派发。** 这本身也是反对"纯 GUI 驱动"的一条架构级理由：
**不在你流里的动作，你无法归因，也就无法显示。**

**第二层（不可解）**：动作一旦进了被控应用，**归因就外包给它了**。
它的日志记不记、记多久、记成什么样，你都不知道也无权过问。
你只知道"我点了这个坐标"，不知道"这个点击在那个应用里变成了什么"。

> 规则：**凡是需要归因的动作，都不该只走 GUI 通道。**
> 这不是洁癖 —— 它是 §13.8 那个权限问题的另一半。

### 13.10 上下文：模型看到的与人看到的不是一回事

**1. 截图是最大的成本变量，而且应该由模型按需索取。**
三个项目代表三种取向：UI-TARS 每步全图（最贵）、
UFO 先过滤控件列表再喂（省）、OpenAI CUA 让模型在代码里主动调
`display()` 才回图（最省）。**最后一种最值得抄** ——
因为模型自己知道"这一步我需要看一眼吗"。

**2. 截图是典型的「可丢弃上下文」。**
它每一轮都能重拍，所以符合 §5.5 里 help 结果那条判据：
**可重新获取的东西，就是最该被 scrub 的东西。**
上下文策略那一层（§15.1 的表）应该把截图单列一类。

**3. 人看到的和模型看到的必须能对上号。**
用户的 GUI 显示窗口实况（或镜像），模型看到的是裁剪缩放后的截图
加结构化控件列表 —— 两者并不相同。对不上，用户就无法判断"它为什么这么做"。

解法：**把模型当时看到的观察结果本身作为事件进消息流**（带 artifact id），
GUI 就能把"模型当时看到了什么"回放给用户。
这一步同时服务 §9 的重放不变量和可解释性，一举两得。

### 13.11 Windows：怎么把一个 GUI 绑到窗口上

#### A. 拿到状态（每一条都有坑）

| 要什么 | 用什么 | 坑 |
|---|---|---|
| 可见边界 | `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` | **别用 `GetWindowRect`** —— Win10+ 它包含隐形缩放边框，比实际可见范围大一圈 |
| 客户区 | `GetClientRect` + `ClientToScreen` | |
| 最小化 / 最大化 | `IsIconic` / `IsZoomed` | |
| 可见性 | `IsWindowVisible` | **它不告诉你窗口是否真的在屏幕上** |
| 是否被藏起来 | `DwmGetWindowAttribute(DWMWA_CLOAKED)` | **虚拟桌面切换时窗口会 cloaked** —— `IsWindowVisible` 仍为真，用户却根本看不到 |
| 焦点 | `GetForegroundWindow` | |
| 归属进程 | `GetWindowThreadProcessId` | UWP 要特殊处理（见后） |
| DPI | `GetDpiForWindow` | 混合 DPI 下不换算必错 |

#### B. 实时追踪：`SetWinEventHook`

用 `WINEVENT_OUTOFCONTEXT` —— **不需要注入 DLL**，回调在自己进程里。
要订阅这些：

| 事件 | 用途 |
|---|---|
| `EVENT_OBJECT_LOCATIONCHANGE` | 移动 / 缩放，**拖动时逐帧触发** |
| `EVENT_SYSTEM_MOVESIZESTART` / `MOVESIZEEND` | 拖动开始 / 结束 |
| `EVENT_OBJECT_DESTROY` / `CREATE` / `SHOW` / `HIDE` | 生命周期 |
| `EVENT_SYSTEM_MINIMIZESTART` / `MINIMIZEEND` | 最小化 |
| `EVENT_SYSTEM_FOREGROUND` | 前台切换 |
| `EVENT_OBJECT_NAMECHANGE` | 标题变化 |
| `EVENT_OBJECT_CLOAKED` / `UNCLOAKED` | 虚拟桌面切换 |

三个坑：

1. **必须过滤 `idObject == OBJID_WINDOW && idChild == CHILDID_SELF`**，
   否则子控件、菜单、tooltip 的位置变化全会打进来。
2. **回调走消息循环** —— 用独立线程 + 自己的消息泵。卡住 UI 线程 = 卡住追踪。
3. `LOCATIONCHANGE` 拖动时是逐帧的 —— 正好拿来驱动跟帧，但别在里面做重活。

#### C. 跟随：不要 reparent

自己的窗口用 `WS_POPUP | WS_EX_LAYERED | WS_EX_TOOLWINDOW`，
目标每次位置变化就 `SetWindowPos` 对齐。**z 序有两种做法，选后者更对：**

- `WS_EX_TOPMOST` —— 简单，但目标被别的窗口盖住时，你的 GUI 还浮在最上面（错位）。
- `SetWindowPos(hwndInsertAfter: 目标窗口)` —— 插在目标正上方，
  目标被盖住时你也被盖住。**代价是 z 序一变就要重新断言。**

#### D. 让可视范围仅限窗口

**裁剪靠 `SetWindowRgn`** —— 给你的窗口设一个矩形或圆角矩形区域。
Win11 的圆角可以照抄目标的 `DWMWA_WINDOW_CORNER_PREFERENCE`。

**还有一条容易被忽略但很关键**：
`SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` ——
**让覆盖层自己不出现在截屏里**。否则智能体截图时会看到自己画的 UI，
**形成视觉反馈环**。

#### E. 「绑定」的第二种读法

如果你想的是**把窗口内容实时显示进你的 GUI**（而不是在旁边浮一层），
那不该用截屏：

| 做法 | 特点 |
|---|---|
| **`DwmRegisterThumbnail`** | DWM 直接把源窗口的实时内容合成进你的窗口，GPU 级，**最便宜** |
| `Windows.Graphics.Capture` | 更通用、能拿纹理，但重得多，且受保护内容抓不到 |

**两者都不转发输入**，输入要另想办法 —— 或者干脆不做输入（只做观察，
控制走 §13.7 的插件 API / LSP）。

#### F. 生命周期

别假设"窗口一直在"。`EVENT_OBJECT_DESTROY` 要接，
必要时拿进程句柄 `RegisterWaitForSingleObject` 等进程退出。

### 13.12 桌宠的现成实现：一个独立窗口 + 一个更窄的 token

cc-haha 有完整的桌宠子系统（`desktop/electron/services/petWindow.ts` 31 KB、
`pets.ts` 51 KB、`PetApp.tsx` 26 KB，外加 8×9 的 spritesheet 图集）。
**但对我们最有价值的不是动画，是它的权限设计** —— 那正好是 §13.6 第一条风险的答案。

#### 关键：桌宠窗口用**独立且更窄**的凭据

`src/server/petAccessPolicy.ts` 的注释写得很直白：

> A pet token is intentionally narrower than the desktop local-access token.
> It can bootstrap the companion, read the bounded session projection,
> and update only pet-owned preferences. **Everything else fails closed.**

具体约束（每一条都值得抄）：

| 面 | 限制 |
|---|---|
| HTTP | 只允许宠物偏好（GET/PUT）、会话列表、单会话状态、健康检查、一条 WS |
| 客户端消息 | 只允许 `user_message` / `sync_state` / `stop_generation` / `ping`，其余 `default: false` |
| 消息字段 | **key 必须精确匹配**（`hasOnlyKeys`），多一个字段就拒 |
| `user_message` | 非空、**不能以 `/` 开头**（不能触发斜杠命令）、≤ 32768 字符 |
| 服务器消息 | **降级过滤**：`permission_requests_snapshot` 里的 `toolRequestIds` / `computerUseRequestIds` 被清空 |
| 错误 | 泛化成 "Pet action failed. Open the session for details." |
| 用量 | `message_complete` 的 token 数字清零 |

**倒数第 3 条是精髓：桌宠连权限请求的 ID 都看不到。**
于是它不可能被当成审批通道 —— 不是靠"文档说它不能批准"，是靠**它拿不到那个句柄**。
文档里也明说："它只是个状态提示和跳转入口，不能替你批准权限。"

我们 §13.6 说的是"同意界面必须由中控绘制、与 agent 内容不可混淆"，
cc-haha 给的是更结构化的一招：**给弱界面发弱凭据，然后 fail closed。**
比"画得让人分得清"可靠得多 —— 因为前者是密码学边界，后者是视觉约定。

#### 窗口实现（Electron 层）

```
alwaysOnTop: true, frame: false, transparent: true,
hasShadow: false, resizable: false, skipTaskbar: true
```

平台差异被 Electron 吃掉了一部分，但没全吃掉：

- `setIgnoreMouseEvents(true, { forward: true })` —— **只有 macOS 走**（透明区域点击穿透并转发）
- `setAlwaysOnTop(true, 'floating')` macOS / `setAlwaysOnTop(true)` 其他
- `setVisibleOnAllWorkspaces(true, ...)` —— macOS

还有两条踩坑记录：窗口是"mascot + 大量透明内边距"，
所以**拖动和边缘吸附必须按 mascot 的实际位置算**，不能按窗口矩形；
保存过位置的窗口在屏幕边缘时，透明内边距会被推出屏幕。

**注意它是 Electron `BrowserWindow`，不是原生 Win32 分层窗口** ——
所以它没走 §13.11 那套 `WS_EX_LAYERED` + `SetWinEventHook`。
Electron 把平台差异吃掉了，代价是有些能力（精确窗口跟随、点击穿透粒度）
要绕或者做不到。

## 14. 电脑操控：观察契约与最小实现

### 14.1 用不用视觉模型

**第一版不用。** 三个理由：

1. **信息本来就不在像素里。** 以 VS Code 为例，你需要的东西（哪个文件开着、
   光标在哪、有没有报错、代码什么内容）全都以文本/结构形式存在于更便宜的地方。
   绕道像素去读，是花钱买更差的信息。
2. **截图读代码不可靠。** 11px 等宽字在 1x 缩放下，视觉模型认字符会出错 ——
   而代码里一个字符错了就是错。**截图可靠传达的是"布局与状态"，
   不是"内容"。**（见 14.2 的分层）
3. **多给一张图不是免费的。** 图片占 token、增延迟，而且对本来能纯文本完成的任务，
   加图会让模型更容易分心。**"模型本来就有视觉能力"不等于"顺手给它看"**。

但要把两个不同的用途分开，它们的正当性完全不同：

| 用途 | 是什么 | 什么时候必须 |
|---|---|---|
| **视觉理解** | 模型读屏幕，知道那儿有什么 | 信息只在像素里时（自绘 UI、画布、无名的图标、游戏、远程桌面） |
| **视觉定位** | 模型输出一个坐标去点击 | 没有元素句柄可用时 |

有扩展 API 或 UIA 的时候，这两个都不需要。

**更精确的说法是：视觉是「像素那一级」的要求，不是整个电脑操控的要求。**
cc-haha 把观察拆成了三个方法（§14.8）：`getAXState()` 只回**无障碍树文本**、
`getScreenshot()` 只回图、两者兼有。**文本是常备通道，截图是可选的。**

对应到 §13.7 那条阶梯：

| 通道 | 要不要视觉模型 |
|---|---|
| 无障碍级（点元素句柄，如 `gN:id`） | **不要** |
| 插件 API / LSP 级 | **不要** |
| 像素级（坐标点击） | **要** —— 坐标来自"模型最近看到的截图" |

还有三个经常被混成一件的东西，分开看会清楚很多：

```
截图（获取像素） ≠ 视觉模型（理解像素） ≠ 坐标点击（需要前两者才能定位）
```

**截图可以不配视觉模型** —— 比如 cc-haha 的 9×9 逐字节陈旧检测，
纯像素比对，不需要模型理解任何东西。
**视觉模型也可以不靠截图** —— 但它通常就没东西可看了。

**结论：观察是一条可插拔的通道，视觉是其中一级，不是地基**（见 14.5）。

### 14.2 以 VS Code 为例：模型该"看"到什么

打开窗口、打开一个工作区之后，"模型看到的东西"要分四层，
**优先级恰好与"像素优先"相反**：

| 层 | 内容 | 成本 | 可靠性 |
|---|---|---|---|
| **窗口层** | 窗口存在、位置、是否前台、是否最小化、**标题栏文本** | 极低 | 高 |
| **编辑器层** | 工作区路径、打开的文件与 dirty 状态、活动文件、光标与选区、诊断、可见范围、终端、调试状态 | 低 | **高且精确** |
| **内容层** | 需要代码内容时**直接读文件** | 按需 | 精确 |
| **像素层** | 布局确认、模态/弹窗检测、动作后验证 | 高 | 低 |

**一个信息量极高但常被忽略的信号：窗口标题。**
VS Code 的默认标题格式是 `<文件> — <工作区> — Visual Studio Code`，
一次 `GetWindowText` 就同时告诉你**当前打开的文件**和**工作区**。
这是整台机器上最便宜的高价值信号。

> 但注意：`window.title` 是**用户可以配置的**。
> 所以它是"便宜信号"，不是"可靠契约" —— 可以用它做提示，不能依赖它做判定。

**「可见范围」（viewport / `visibleRanges`）值得单独留一格。**
"文件里有什么"和"用户此刻屏幕上能看到哪几行"是两回事。
当智能体说"你看到的这段代码"时，它指的是后者。
这正是 §13.10 那条"人看到的和模型看到的要对上号"的具体落点。

### 14.3 一个必须自己验证的事实：Electron 的 UIA 树几乎是空的

这条会直接改变阶梯的顺序，而且值得你亲手验一次。

Chromium / Electron **只在探测到辅助技术客户端时才构建无障碍树**。
所以对一个刚打开的 VS Code 窗口做 UIA 遍历，通常只能拿到顶层窗口
（`Chrome_WidgetWin_1` 之类），内部是空的 —— 没有文件树、没有编辑器、
没有菜单项。

**也就是说：UFO 那套"UIA 优先"的策略，在原生 Win32 / WPF 应用上成立，
在 Electron 应用上基本失效。** 而 VS Code、Slack、Discord、Notion
这一整类现代应用都是 Electron。

绕过办法（都要多花功夫）：用 `--force-renderer-accessibility` 启动，
或者让被控应用自己暴露接口。**而后者恰好就是下一节要讲的那条路。**

### 14.4 最小可行版本

目标是**最小代价验证三件事：观察通道、控制阶梯、归因三字段**。

**不做**：不 reparent、不做桌宠、不碰像素、不碰 UIA。

```
观察   GetWindowText（标题）        ← 窗口层，一行代码
     + 扩展提供的结构化快照         ← 编辑器层，主力
     + 按需读文件                  ← 内容层，精确

动作   全部走 VS Code 扩展 API      ← route = extension_api（阶梯最上一级）

归因   每个动作事件带 capability / binding / consent（§13.9）

通道   扩展 ↔ 本地 WS ↔ 中控       ← 复用 EasyTerminal 已有的 WS 桥
```

**结构化的编辑器快照大致长这样**（示意，不是最终字段）：

```
workspace: D:\proj
active:    src/main.rs  (dirty)
open:      [src/main.rs, Cargo.toml, tests/smoke.rs]
cursor:    line 42, col 8;  selection: 42:1-45:12
viewport:  lines 30-58            ← 用户此刻看得见的
diagnostics: 2 errors, 1 warning  (前 5 条带位置与消息)
terminal:  1 个, cwd = D:\proj, 最近 20 行
debug:     无
```

这大概是百 token 级，而且可以**按需裁剪**（只要光标附近那几行）。
对比之下，一张 1920×1080 的截图是千 token 级，而且每轮都要重付，
还读不准代码。

**验收标准建议定成**：智能体能准确回答"当前打开的是哪个文件、光标在哪、
有没有报错"，并且能完成**一次引用感知的重命名**。
后半条是关键 —— **它正是 GUI 点击做不到、而插件 API 天生做得到的事**，
所以它能一次性证明这条技术路线选对了。

**后续三级的加法，按需踩：**

| 阶段 | 加什么 | 换来什么 |
|---|---|---|
| 二 | UIA | 快速打开、设置面板、原生对话框 —— 扩展 API 够不到的那部分 |
| 三 | 截图 | 动作后验证、"它当时看到了什么"回放（§13.10） |
| 四 | 像素 / 合成输入 | 完全没有 API 的应用，兜底 |

### 14.5 观察通道也是一类实例

和工具一样，观察通道应该是注册进来的实例，而不是写死的代码路径：

```
kind = observer
capabilities = { 窗口标题, 结构化状态, 控件树, 截图, 文件读取 }
route = 这份观察来自哪一级（对应 §11.2 的 route）
cost  = 粗估 token 成本，供中控挑选
```

这样中控就能按"目标是什么应用 + 这一轮要什么信息"选最便宜的可靠通道，
而不是永远走最贵的那条。**"一切皆实例"这条原则在这里同样适用 ——
连"看"的方式都是可注册、可替换的。**

### 14.6 知道路径容易，限制范围难

> **读之前先分清**：本节讨论的是**硬边界**（"绝对不许出去"）。
> 如果你要的只是"像已有 agent 那样指定一个工作区"，那看 §14.7 —— 简单得多。
> 两者是不同的问题，别混。

#### A. 知道路径：有多个独立来源

| 来源 | VS Code | Visual Studio |
|---|---|---|
| **应用 API（权威）** | `workspace.workspaceFolders[].uri.fsPath`；多根时是数组；`.code-workspace` 看 `workspaceFile` | **`DTE.Solution.FullName`**（COM 自动化） |
| 进程命令行 | `code.exe D:\proj` | `devenv.exe D:\proj\foo.sln` |
| 窗口标题 | 默认只给 `${rootName}` —— **只有名字，没有路径** | 同样只有名字 |

**"名字 ≠ 路径"这条别混。** 默认窗口标题里的 `${rootName}` 是**文件夹名**，
同一台机器上两个同名项目就分不出来了。要路径必须走应用 API 或进程命令行。

顺带一个对照：**VS Code 要靠扩展，Visual Studio 可以靠 COM 自动化
（`EnvDTE` / `DTE2`）** —— 后者比 UIA 好用得多。
这和 §14.3 的结论正好互为镜像：Electron 靠扩展，原生应用靠它自己的自动化接口，
**UIA 在两边都只是兜底。**

#### B. 但"只在这个项目里"先要定义"里面"

这三件事让"项目"的边界天生模糊：

- **解决方案可以引用目录外的项目** —— `<ProjectReference Include="..\..\Shared\...">`
- **工作区可以多根** —— VS Code multi-root，"这个项目"是哪一根？
- **项目可以 file link 引用外部文件** —— `<Compile Include="..\..\foo.cs" />`

#### C. 真实工作流必然越界的地方

即使边界定义得再清楚，一个能用的 IDE 会话也会碰到外面：

| 越界的东西 | 例子 |
|---|---|
| 构建缓存 | `~/.cargo`、`~/.nuget`、全局 npm 缓存 |
| 临时目录 | `%TEMP%` |
| IDE 自身状态 | `%APPDATA%\Code`、设置、扩展存储、日志 |
| 源生成器 / 分析器 / MSBuild 任务 | 可以写任何地方 |
| git 凭证 | 凭证管理器、`~/.gitconfig` |
| 网络 | 还原依赖 |
| **终端** | **一旦开放，就是任意** |
| 调试 | 拉起任意进程 |

> 结论：**"一切行动只在这个项目里"对真实 IDE 工作流做不到 ——
> 不是实现难度的问题，是工具链本身就在外面。**

#### D. 但有可达到的版本，按强度排序

| 强度 | 手段 | 说明 |
|---|---|---|
| **强** | OS 沙箱（§5.8） | 物理条件：独立用户 / 容器，只把项目目录挂进去。**唯一能真正说"只能"的做法。** 代价是 IDE 变难用（缓存写不了、扩展装不了、凭证读不到） |
| **中** | **能力面没有出口** | 例：第一版只管编辑，而**编辑 API 只能改已打开的文档 URI** —— 它结构性地写不到别处。不是靠检查做到的，是没有出口 |
| **弱** | 路径检查 | 目标 URI 必须在 workspace 之下。**要做，但要标注它是"防手滑"不是"防越权"** —— symlink / junction 能绕，构建会写到外面逼你加白名单，而且管不住任何带终端的能力 |

**关键洞察：收窄能力面比检查路径可靠得多。**
路径检查是字符串层面的判断（§5.8 那个老问题的变体）；
"这个 API 只能改已打开的文档"是结构性的。

这也解释了你上一轮定的 MVP 为什么天然合规：**第一版只管编辑 + 读诊断，
能力本身就没有出口，所以"只在这个项目里"基本自动成立。**
一旦开放终端 / 任务 / 调试，出口就出现了 —— 那时只剩沙箱一条路。

#### E. 一个实用建议：范围默认取 git 仓库根

比 IDE 工作区根更稳定、更有意义，而且**开发者自己就是用这个边界思考的**。

- 好处：用户打开子目录时范围不缩水；多根工作区不会把范围搞模糊。
- 代价：需要白名单那些"合理地写在外面"的东西（缓存、临时目录）。

### 14.7 工作区：不是边界，是语境

（回应"'我想要的其实就是已有 agent 里指定工作区'那种效果"）

**那答案简单得多：不只是知道路径，而且不用你告诉它。**

已有 agent 里工作区是**你指定的**（`--cd`、打开文件夹）。
托管的第一个好处是 **范围从 IDE 读出来**，用户不必再声明一次 ——
`workspace.workspaceFolders` / `DTE.Solution.FullName` 就是权威来源。

**第二个好处更重要：范围是活的。**
用户在 IDE 里切文件夹、加一个根、换一个解决方案 —— 范围跟着变。
手动指定的工作区做不到，它在启动 agent 那一刻就冻结了。

**第三个好处最容易被忽略：IDE 给的不只是路径，是"用户此刻的工作集"。**

- 打开着哪几个文件 ← **这就是用户当下的注意力范围**
- 当前活动文件、光标位置、选区
- 各文件的 dirty 状态（哪些有未保存的改动）
- 诊断（有哪些错误）
- 终端与调试状态

对比一下起点：

| 方式 | 智能体一开始拿到的 |
|---|---|
| 手动指定工作区 | "给你一个目录，你去探索" |
| **托管 IDE** | "用户在改这 4 个文件，光标在 main.rs:42，另有 3 个错误" |

**这是数量级的效率差 —— 而它才是托管 IDE 的真正理由。**
不是限制智能体，是让它一开始就站在用户的位置上。

#### 实现上三条，都不难

1. **workspace 本来就是一个实例**（§3 的清单里有它）。托管时从 IDE 填充它，
   不需要新机制。
2. **提示词里声明范围，但变更走事件。** 用户在 IDE 里换了工作区，
   不要重写 system 段 —— 追加一条"范围现在是 X"的事件，
   复用 §5.4 那套（**和工具名册变更走完全同一条路**）。
3. **范围 ≠ 权限，分开。** 这是上一轮搅在一起的地方：

   | | 管什么 | 是什么 |
   |---|---|---|
   | **范围** | 默认基准、搜索面、语境、持久化归属 | **默认值** |
   | **权限** | 能不能写、要不要问人 | **门控与沙箱的事** |

   所以越界不是"违规"，只是"超出默认语境"。正常做法是：
   相对路径按工作区解析；要碰外面的东西就写绝对路径，它照做，
   **但这件事会显式出现在消息流里**。
   真正需要拦的是危险写操作（那是门控的事），不是路径本身。

### 14.8 一个已经做完的实现：cc-haha（`D:\agent\refer\cc-haha`）

Claude Code Haha 把 Codex 的原生 Computer Use **逆向复刻**了一遍，两套实现都开源：
MCP 版（`src/vendor/computer-use-mcp/`）+ 原生版（`native/cu-helper/`，Swift 守护进程）。
它既印证了前面几节的判断，又补上了我们还没定的几个问题。

#### 它印证的三件事

1. **工具暴露收敛到极少 schema。** macOS 原生路径向模型只公布 `js` 和 `js_reset`
   两个工具，理由写得直白："减少重复的逐动作 schema"。
   所有动作藏在持久 JavaScript 会话里 —— `await app.drag()` 可以在**一次调用内循环**。
   **这正是 §5.4 / §5.8 的冻结核心集 + 调度器，被独立得出的同一个结论。**
2. **动作不自动观察。** "动作本身不自动观察，脚本在需要决定下一步时显式请求状态。"
   —— 等同 §14.1 里 OpenAI CUA 的 `display()` 按需截图。
3. **坐标只给模型一种约定。** `pixels` 或 `normalized_0_100` 二选一，
   原文："The model sees ONE convention and **never learns the other exists**"，
   而且工具描述与执行器读同一份冻结配置，避免"描述说一种、执行器按另一种换算"。

#### 它补上的一件事：权限粒度按**应用类别**硬编码

这直接回答 §18 的第 15 条。三档的含义和理由都值得抄：

| 档 | 允许 | 哪些应用落这档 | 理由 |
|---|---|---|---|
| `read` | 能被截屏看到，**不能交互** | **浏览器** | 点网页该走浏览器扩展（DOM 级），不该走像素 |
| `click` | 可见 + 左键点击 + 滚动，**不能输入** | **终端 / IDE** | 能点 Run、能滚日志，但 `type("rm -rf /")` 被挡住 |
| `full` | 一切 | 其余 | —— |

**关键在于：档位由应用类别决定，用户不能改**
（"Hardcoded by category at grant time — the approval dialog displays the tier
but the user cannot change it"）。

这一条几乎是 §5.8 "终端等于任意"那个结论的**直接落地**：它不用沙箱管住终端，
而是**根本不给终端打字的能力** —— 要跑命令就走 Bash 工具（那里有门控）。
**用"减少能力"代替"加强审查"**，和"收窄能力面比检查路径可靠"是同一条思路。

而且他们把绕过口也堵了：挡住打字之后，终端菜单里还有个 Paste 按钮是普通左键可点的 ——
于是加了 **clipboardGuard**：`click` 档应用位于前台时暂存并清空剪贴板。
**"挡一层不够，得想下一层怎么绕"** —— 这段值得完整读。

#### 观察边界 ≠ 输入边界（而且他们如实标注了泄漏）

| 平台 | 截图过滤 | 后果 |
|---|---|---|
| macOS | `native` | 截图时在合成层排除未授权应用窗口 |
| Windows | **`none`** | **截图可能包含所有可见窗口** |

原文一句：**"Windows 的『输入不会落到未授权应用』不能推导为『截图不会泄露其他窗口』。"**
用户指南里也直说：Windows 上开始前请自己关掉或最小化敏感窗口。

这是 §13.10 "模型看到的"那一格的**隐私版本**，也是个好示范 ——
**能力没做到就说没做到，不靠文档措辞蒙混。**

#### 另外两个细节

**截图几何必须整体保存。** "截图尺寸、逻辑显示尺寸、缩放比例和显示器原点
**必须作为一个整体保存**，否则 Retina 或多显示器环境会点击到错误位置。"
他们跨进程重启时只持久化尺寸（`ScreenshotDims`，去掉 base64），让坐标换算活着。

**陈旧像素检查。** 点击前做 9×9 逐字节比较，检测"模型看过截图之后界面变了"。
默认关闭，而且有一条很对的容错原则：**校验失败绝不能阻断动作**
（解码失败 → 跳过校验 → 点击照常执行）。这正是 §11.2
"`unverifiable` 既不等于成功也不等于失败"的应用。

#### 对你有用的两件额外事实

**1. Teach 模式**（接 §12 的 GUI 与文字）：智能体请求教学授权 → 在屏幕上画提示
→ 等用户点 Next → 执行动作 → 返回新截图。**它同时是同意界面和教学界面**，
走独立授权入口、不继承剪贴板与系统键标志。
§13.6 那条"同意界面必须与 agent 内容可区分"有了一个现成参考。

**2. 一个必须知道的事实**：这份文档明确写着，官方 Codex 的**原生服务不在开源仓库里** ——
"公开的 Codex CLI 和 App Server 源码包含 MCP 集成、工具调度及消息处理，
但**不包含这份原生服务的鼠标事件实现**"。所以 cc-haha 是逆向出来的。
**你之前拉 `openai/codex` 拿到的是 harness，不是电脑操控实现**；
后者目前只有这个第三方复刻可读。

### 14.9 cc-haha 在 Windows 上是怎么做的

#### 分层：策略与机制分离

```
模型 / MCP Client
  ↓ 工具定义与参数校验          tools.ts
  ↓ 会话授权与安全调度          toolCalls.ts        ← 所有授权与策略都在 TypeScript
  ↓ Host 集成                  src/utils/computerUse/
  ↓ Python Bridge             pythonBridge.ts      ← venv、依赖、子进程协议
  ↓ 平台 Helper               mac_helper.py / win_helper.py
```

原文明说：**"Helper 每次调用是一个有边界的子进程请求。它不会直接读取模型状态；
所有会话授权和动作策略都在 TypeScript 层决定。"**
—— 执行器只负责"做"，不做任何判断。这正是 §11.2 那条**驱动报告事实、harness 决定意义**。

**平台实现是不对称的**：macOS 是原生 Swift 守护进程（没有 Python 路径），
**Windows 是纯 Python**（`runtime/win_helper.py`，1724 行）。技术栈：
`mss`（截图）、`pyautogui`（合成输入）、`pywin32`（窗口枚举/矩形）、
`psutil`（进程）、`pyperclip`（剪贴板）、`screeninfo` + `shcore.GetDpiForMonitor`（显示器）。

#### 修正：Windows 侧没有控件树，它是纯视觉的

上一节说"cc-haha 把观察拆成 `getAXState()` / `getScreenshot()`" —— 那是对的，
但**那是 macOS 的事**。查证结果：

`win_helper.py` 里唯一两处 `accessibility` 命中都是**权限声明**
（"Windows does not require explicit accessibility/screen-recording permission"），
**不是控件树访问**。整个 Windows 侧没有 UIA，只有：

```
观察 = mss 截图
动作 = pyautogui 坐标注入
窗口 = pywin32 枚举/矩形（只用来选目标和算坐标，不用来读内容）
```

原因也清楚：macOS 那套 AX 是因为他们**逆向复刻 Codex 的原生 macOS 服务**
（`AXTree.swift` 86 KB、`AXAction.swift` 75 KB），有明确的对照物；
Windows 上没有对应的官方实现可抄，所以只做了最便宜、能跑通的那条。

> **所以：cc-haha 的 Windows 实现是纯视觉的。控件树是它 macOS 分支的专利。**

这不是小事 —— 它说明"用无障碍树免掉视觉模型"这条路，
**在 Windows 上得自己从头搭，没有现成的可以照抄**。好消息是有人搭过（见 §14.10）。

#### 它自己写下的最重要的一句

`win_helper.py` 的头部注释解释了一切：

> macOS 用 `CGEvent.postToPid` **直接把输入投递进目标进程**，不动真实光标，
> 也不改变前台应用。**Windows 没有等价物。**
> `pyautogui` 走系统级合成输入，会注入全局输入流并**挪动那唯一一个真实光标**。
> 因此智能体**和用户共用鼠标键盘，而且无法验证自己发出去的东西有没有到达**。

这不是实现细节 —— 它决定了一切。由此长出两个 macOS 侧不存在的机制：

| 机制 | 作用 |
|---|---|
| **`ForegroundLease`** | 物理输入与动作重叠时中止 —— 交错的输入流会产生"双方都没打算发出的点击" |
| **`ensure_point_on_screen` / `ensure_target_window_reachable`** | 当投递已知不可能时**直接拒绝发送** |

理由写得很直白：

> **`SendInput` 无条件报告成功，而给一个根本没送到任何地方的输入回一句
> 「动作已完成」，比报错更糟。**

**这句话就是 §11.2 的核心，被一个真实项目用血换来的版本。**
它也解释了为什么 Windows 侧的结果必须区分
`confirmed` / `unverifiable` / `suspected_noop`（§11.2 那五态）。

#### 两个细节值得单独记

**UWP 的进程归属**：`_window_process()` 枚举子窗口时给
`Windows.UI.Core.CoreWindow` 类名更高优先级 —— 因为 UWP 应用的真实进程
藏在 `ApplicationFrameHost` 的框架窗口后面。
**这印证了 §13.2 那条"UWP 不好对付"**，只不过他们不是为了 reparent，是为了认出它属于谁。

**DPI 先行**：进程一启动就把自己设成 `PER_MONITOR_AWARE_V2`，
注释是 "Keep capture, SendInput, and overlay coordinates in physical pixels"。
—— 和 §14.8 那条"截图几何必须整体保存"是同一个坑的两端。

#### 一个安全上的落差

macOS 侧有原生守护进程做**进程身份校验和客户端 attestation**（`ClientAttestation.swift`）、
以及合成层的截图过滤。**Windows 侧全部落在 Python 层**，只有前台应用白名单 + 三档权限。
也就是说 **Windows 的安全强度低于 macOS**，而且这是"没有原生实现"造成的结构性差距，
不是没写。自己实现时要清楚这一点。

### 14.10 Windows 的控件树：UFO 就是那个仓库

§14.9 说 Windows 上得自己搭控件树 —— **其实已经有人搭好了，而且就在参考库里**：
`D:\agent\refer\UFO`。

它的整条链子是：**建树 → 拍平 → 按计划过滤 → 增量 diff**。

**依赖**（`uiautomation==2.0.18` + `comtypes==1.2.0` + `pywin32`）——
`uiautomation` 是 `yinkaisheng/Python-UIAutomation-for-Windows` 的 pip 包，
它在 `comtypes` 之上封装了原生 UIA。

**建树**（`ui_control/inspector.py`）：
`UIABackendStrategy` 直接拿 `UIAutomationClient.IUIAutomationElement` 递归遍历，
并且用 **cache request 批量缓存属性** —— 这一步很关键，不加缓存的话每次读属性
都是一次跨进程调用，大树会慢到不可用。

**节点形状**（`ui_control/ui_tree.py`）：

```json
{
  "id": "...",
  "name": "...",              // 可访问名
  "control_type": "Button",   // 控件类型
  "rectangle": { "left": .., "top": .., "right": .., "bottom": .. },
  "children": [ ... ]
}
```

**然后三个加工步骤**：

| 步骤 | 方法 | 作用 |
|---|---|---|
| 拍平 | `flatten_ui_tree()` | 变成列表，方便喂模型和按 id 引用 |
| 增量 | `ui_tree_diff()` / `apply_ui_tree_diff()` | **只传变化的部分**，对应 cc-haha 的 `AXTreeDiff.swift` |
| 过滤 | `control_filter.py` | Text / Semantic / Icon 三种过滤器，按当前计划先筛再喂（§14.8） |

**这套东西对我们是直接可用的**：它同时解决了 §14.3 那个"Electron 的 UIA 树是空的"
之外的情况 —— 原生 Win32 / WPF / UWP 应用能拿到相当完整的控件树，
而且 `rectangle` 字段让"控件树"和"坐标点击"能对接上：
**用树来理解，用坐标来操作**（UFO 的 hybrid 就是这个意思）。

顺带把几个独立候选列出来（都验证存在，按需再拉）：

| 仓库 | 是什么 |
|---|---|
| `yinkaisheng/Python-UIAutomation-for-Windows` | UFO 用的那个库本体，文档和例子最全 |
| `pywinauto/pywinauto` | 另一套 Python 自动化库 |
| `FlaUI/FlaUI` | .NET 侧的主流选择 |
| `microsoft/accessibility-insights-windows` | 微软官方检查工具（看树用） |
| `microsoft/WinAppDriver` | 官方驱动式自动化 |

### 14.11 UIA 的真实能力边界

#### 它怎么"认出"控件的：不是认，是问

`Python-UIAutomation-for-Windows` 是微软 UIAutomation 的 **COM 客户端**
（`IUIAutomation` / `IUIAutomationElement`，`bin/` 里带两个 VC140 的
`UIAutomationClient.dll`，经 `comtypes` 调 COM）。

**它不分析像素。** 它向应用**请求应用自己声明的 UIA provider**：
"你有几个孩子、你叫什么、你支持哪些 pattern"。没有 OCR、没有图像分析、没有猜测。

> **所以覆盖率 = 应用有没有实现 provider。** 这一点决定了后面所有结论。

库的 README 自己列了覆盖范围，而且写得很诚实：

> MFC、Windows Form、WPF、Modern UI (Metro)、Qt（**部分**）、
> Firefox（≤56 或 ≥60）、Chrome，以及 Electron 系
> （**需要 `--force-renderer-accessibility` 参数**）

没有原生实现的应用靠两座桥补：

| 桥 | 暴露成 | 说明 |
|---|---|---|
| **MSAA（`IAccessible`）** | `LegacyIAccessiblePattern` | `Role` / `State` / `DefaultAction` / `DoDefaultAction` |
| **HWND 默认 provider** | 标准控件类型 | Button / Edit / ListBox 等由系统提供实现 |

**另一个硬限制**：README 明说**要以管理员身份运行**，
否则可能"枚举不到控件或读不到控件信息"。—— 又是 UIPI，
和 §5.7、§13.2 是同一道墙，这已经是它第三次出现了。

#### 元素动作阶梯（对 §13.7 那条阶梯的细化）

UIA 把"看得见"和"点得动"分成两件独立的事，而且**给了你查询能力**：
`IsInvokePatternAvailableProperty`、`IsLegacyIAccessiblePatternAvailableProperty`…
可以先问"能不能"，再决定"怎么动"。

于是**单个元素内部**还有一条阶梯：

| 级 | 手段 | 说明 |
|---|---|---|
| 1 | `InvokePattern.Invoke()` | 语义级，不依赖坐标、不怕遮挡，最可靠 |
| 2 | `LegacyIAccessiblePattern.DoDefaultAction()` | **MSAA 桥**，覆盖 UIA 支持不好的老应用 |
| 3 | `SelectionItemPattern.Select()` / `TogglePattern.Toggle()` | 特定控件的语义动作 |
| 4 | `SetFocus()` + 键盘 | 菜单之类有时候这个最稳 |
| 5 | **坐标点击** | 兜底：`BoundingRectangle` 中心，或 `GetClickablePoint()` |

第 5 级就是**这个库自己的 `Click()` 在做的事** —— 它按 `BoundingRectangle`
算中心（带 `ratioX` / `ratioY` 微调），然后发真实鼠标事件。
**连 UIA 官方风格的工具，最后一公里也是坐标。**

#### 那"完美融入背景但可点击的一行文字"怎么处理

分三种情况，而它们对应三种完全不同的处理：

| 情况 | 树里看得到吗 | 能调用吗 | 怎么办 |
|---|---|---|---|
| **真控件但没声明可点击**（如 WPF `TextBlock` 挂了点击处理） | 能（有名字/矩形） | **不能**（`IsInvokePatternAvailable` 为假） | 用树**定位**，用坐标**点它的矩形** |
| **自绘 UI**（Canvas / DirectX / 游戏） | **不能** —— 整个区域只是一个元素 | —— | **只能靠视觉**（UFO 的 OmniParser 路线） |
| **只实现了 MSAA 的老应用** | 能 | 可能只能走 `DoDefaultAction` | 试第 2 级，通常比坐标点更可靠 |

**第一种最常见，也最容易被高估**：UIA 帮你**找到**它，但**不保证能操作**它。
"有矩形、没有 Invoke"是一个完全正常的组合 ——
这时候正确做法不是放弃，而是**降级到坐标点击**。这正是 UFO 说的 hybrid。

第三种顺带补上我们之前漏掉的一级：
`DoDefaultAction()` 比坐标点击更可靠，因为它进的是**应用自己的动作处理**，
而不是模拟鼠标。**值得排在坐标之前试。**

#### 两个"树本身"的工程问题

**树可能又深又大** → 所以这个库的 `WalkTree` 是**非递归实现**的
（`getChildren` 或 `getFirstChild` + `getNextSibling` 回调、`maxDepth`、`yieldCondition`），
递归在深树上会爆栈；UFO 那边则用 cache request 减少跨进程往返。
两种手法解决的是同一个问题的两端。

**名字可能是空的** → 真实的树里有一堆 `Name=""` 的 `Pane` / `Custom`。
这时只能靠 `ClassName` / `AutomationId` / 位置 / 同级顺序来认。
**而且这个库不管"相关性"** —— 它给你 300 个控件，
哪个是你真想要的那个，是 UFO 的 `control_filter` 干的活（§14.8）。

### 14.12 「没考虑过自动化的应用」会失效吗

**答案不是二分的，而且"有没有考虑过自动化"这个判据是错的。**

真正决定有没有树的，是**这个应用建在什么 UI 框架上**。
原因是 UIA 首先是**无障碍**接口，而框架的无障碍支持通常是**白送的**。

库的 README 直接引了微软的原文：

> Microsoft includes a provider for each of the standard controls that are supplied
> with Microsoft Win32, Windows Forms, and Windows Presentation Foundation (WPF).
> **This means that the standard controls are automatically exposed to UI Automation
> clients; you do not need to implement any accessibility interfaces for the standard controls.**

也就是说：**用了标准控件的应用，哪怕开发者做梦都没想过自动化，树也是白拿的。**
记事本、资源管理器、绝大多数 WinForms / WPF 应用都属此类。

#### 四个带，而不是两分

| 带 | 情况 | 树 | 例子 |
|---|---|---|---|
| **1** | 标准框架 + 标准控件 | **白拿，质量好** | 记事本、资源管理器、WinForms / WPF 应用 |
| **2** | 框架有 provider，但要条件 | **开一下就有** | Electron / Chrome（`--force-renderer-accessibility`）；Qt（插件 + 自绘控件要自己实现） |
| **3** | 有树但是垃圾 | **拿得到，用不了** | 一堆无名 `Pane`、角色说谎、虚拟列表只暴露已渲染项 |
| **4** | 自绘 / 无 provider | **真失效** | 见下 |

作者自己给的第 4 带判据最干脆（readme_cn）：

> 这个软件必须实现 UI Automation Provider 才能支持 UIAutomation。
> **如果一个软件是用 DirectUI 实现的，但没有实现 UI Automation Provider，
> 那么这个软件是不支持 UIAutomation 的。**

#### 第 4 带具体是哪些

- **游戏 / 3D 应用**（DirectX / OpenGL / Vulkan / Unity / Unreal）—— 整个窗口一个元素。
- **CAD、图表、图像编辑器**这类画布型应用。
- **DirectUI 自绘且没实现 provider 的**。
- **远程桌面 / 虚拟桌面** —— 被控应用的树**根本不过 RDP 边界**，
  你只拿到一张位图。**这一条最容易被忽略，也最绝对。**

但还有一个比"整个应用失效"更常见、也更麻烦的情况：

> **一个 WPF 应用里，某个自定义控件没有重写 `OnCreateAutomationPeer` ——
> 树会从那里断掉。**

**所以失明是按子树发生的，不是按应用发生的。**
这一条直接决定了应对方式：**按子树降级，而不是按应用切换。**
盲区那一块走视觉，然后把结果**包回树的形状**（UFO 的
`convert_to_virtual_uia_elements` 正是干这个），下游代码就不必知道那块是猜的。

#### 作者自己承认的死角

readme 里有一句很诚实的注释：

> 如果遇到 COMError，一般是没有以管理员权限运行 Python，
> **或者这个控件没有实现 pattern 的方法（如果是这种情况，基本没有解决方法）。**

这就是 §14.11 那个"有矩形、没有 Invoke"的第一种情况 ——
树里有它，但没有任何语义动作可走，**只能降级到坐标点击**。

另外树的快照会失效：`Refind()` 是必须的 —— 界面一变，旧的元素引用就不成立了。
这对应 cc-haha 那条"UI 变了要重新截图"（§14.8），但这里是**重新枚举**。

#### 先量，别假设

这个库自带 `automation.py`，对着任何应用跑两条命令就知道它在哪个带：

```powershell
python automation.py -c -t3      # 看光标下的控件（-t3 = 等 3 秒让你把鼠标放上去）
python automation.py -t3 -d2     # 看前台窗口往下两层
```

**十秒的事，比讨论快得多。** 作者的测试清单里就有 Wireshark 3.0（Qt 5.12）
和 GitHub Desktop（Electron）—— 都是"第三方框架且需要额外条件"的典型，
说明第 2 带实际可用，只是要先解决前置条件。

| 应用 | 节点数 | 结论 | 提供方 |

| **Maskface**（自研 egui 应用） | **53** | **完整，可 Invoke** | Unidentified Provider (`maskface.exe`) |

#### 四条反直觉的发现

**1. 自研的 egui 应用有完整控件树。** Maskface 是 Rust + egui，
实测 53 个节点、31 个有名字、30 个可 `Invoke`，按钮名全在
（"打开工作区"、"添加文件夹"、"隐藏 Agent"、"远程通道"…）。
这是 **AccessKit** 的功劳 —— 现代 egui 默认集成它。

**这条推翻了"自绘 UI 必然没有树"的直觉**，而且有个好处：
**你自己造的 GUI 会自动是可自动化的，不需要额外工作。**

**2. 同是 Chromium，VS Code 空而 Edge 满。** 差别在触发：
Chromium 只在检测到辅助技术客户端、或拿到 `--force-renderer-accessibility`
时才建树（§14.3）。这次 VS Code 没被触发。
→ **下一个对照实验很清楚：用带 flag 的方式重启一次 VS Code 再测。**

**3. 深度会骗人。** Edge 在 8 层时只有 100 个节点、`Document` 是空的，
看起来像"网页内容拿不到"；放到 16 层变成 281 个节点、61 个文本节点，
内容全出来了。**探针必须探够深，否则会得出正好相反的结论。**

**4. 微信是教科书级的第 4 带案例。** 整窗只暴露两个节点，
关键那个叫 `MMUIRenderSubWindowHW` —— 腾讯自己的 MMUI 自绘框架，
里面什么都没有。**正是作者说的 DirectUI 情况**（§14.12）。

**附带**：README 那条"要以管理员运行"是**可能失败**而非必然 ——
这次非管理员跑通了全部枚举和属性读取。

### 14.14 不用 Python 的实现路线

#### 一条必须先记住的硬规则

库作者在 `demos/uiautomation_in_thread.py` 里写得很直白：

> 如果你想在新线程里使用 UI 控件，先创建一个 `UIAutomationInitializerInThread`。
> **但你不能使用在另一个线程里创建的 Control 或 Pattern。**
> 所以不能在主线程建一个 Control，再传给新线程去用。

**UIA 元素是线程亲和的**（绑定到创建它的 COM 单元）。这一条直接决定多智能体的架构 ——
它意味着**元素句柄不能跨智能体共享**。

#### 所以形状只能是：一个目标窗口 = 一个进程

```
中控 (Rust)
  ├── helper: VS Code   独立进程 / 独立 COM 单元 / 元素只在本进程内有效
  ├── helper: Edge
  └── helper: 微信
        ↕ 行分隔 JSON（stdin/stdout 或命名管道）
```

进程优于线程的三个理由：

1. **COM 单元天然隔离**，不用手动管 `CoInitializeEx` 的单元模型；
2. **崩溃隔离** —— UIA 调用在目标应用忙时会挂住，
   **一个 helper 挂住不能带走中控**；
3. **多智能体 = 多个 helper**，没有共享可变状态，也不需要锁。

这也正是 cc-haha 和 cua 的形状（§14.9、§14.8）：**上层决定策略，下层只执行。**

#### Rust 侧基本是现成的

`leexgone/uiautomation-rs`（已拉到 `D:\agent\refer\uiautomation-rs`）
是基于 `microsoft/windows-rs` 0.62 的封装，覆盖面**正好是我们需要的全部**：

| 我们需要 | crate 里对应 |
|---|---|
| 建树 | `UITreeWalker`（`get_first_child` / `get_next_sibling`） |
| **属性缓存** | `samples/uia_cached_print` —— 就是 cache request 的等价物（§14.10） |
| 动作 | `patterns.rs`（59 KB，全 pattern） |
| **事件订阅** | `events/` + `samples/uia_event_handler`、`uia_async_event` |
| 键盘鼠标 | `inputs.rs`（46 KB） |
| 截图 | `screenshots.rs` |
| 按进程过滤 | `processes.rs`（feature `process`） |
| 剪贴板 | `clipboards.rs` |

**所以"不用 Python"这件事基本不用自己写底层**，只需要写三样：

1. helper 的 JSON 行协议（对应 cc-haha 的 `command + payload`）；
2. 中控侧的 helper 生命周期管理（拉起来、健康检查、回收）；
3. 把树加工成给模型看的形式（拍平 + 过滤，对应 UFO 的 `control_filter`）。

#### TS / Node 的位置

按你的排序，它确实该在 Rust 之后 —— 而且有个额外理由：
**UIA 是 Windows COM，Node 要碰它必须走 NAPI 原生插件，等于还是要写 Rust。**
那一层不如直接留在 Rust 里。**TS 只负责 GUI 与协议，不碰 UIA。**

### 14.15 续测：从窗口里「能看到什么」

把探针的采样上限放开后又跑了一遍。**结果比"能不能拿到树"重要得多** ——
它证明了观察这一侧的风险被严重低估了。

#### 四个层级的泄漏，逐级加重

**① 窗口标题：最廉价的一行。**
VS Code 那个"几乎空"的窗口只有 19 个节点，但标题是
`3.cpp - 数据结构与算法 - Visual Studio Code` ——
**项目名和当前文件名全在里面。** 一次 `GetWindowText`，零成本。

**② 应用自己的状态：自研应用的暴露最彻底。**
Maskface 只有 53 个节点，但因为 AccessKit 集成得好，它报出了：

```
工作区路径  D:/Android/Sandbox/tasks.blackboard   （出现两次）
当前模式    单例模式 · 任务目录 tasks.blackboard · code
全部按钮    打开工作区 / 添加文件夹 / 保存 / 隐藏 Agent / 远程通道 /
            终端面板 / 单例 / 群聊 / 弹出 / 选择 / 链接 / 新建 / 编辑 /
            断开 / 销毁 / 自动排布 / 复位缩放
操作提示    右键/F2 编辑 · 滚轮缩放 · 点线断开
```

**"节点少"和"信息少"不是一回事。** 这 53 个节点把项目路径、
工作模式、以及整个功能面都交出去了。

**③ 书签与历史：一份用户画像。**
Edge 的书签栏给出 11 条，能直接推出身份与技术栈：
`DeepSeek 开放平台`、`Kimi API 开放平台`、`登录|雨云`、
**`山东大学正版软件平台`**、**`SDUOJ`**、`元景大模型MaaS平台`、
`HYEKU-黑峡谷云驱动`、`Web前端学习路线`。

**④ 整页的第三方内容：用户一个字没输入。**
这才是最值得警惕的 ——

- Edge 新标签页：MSN 新闻流 **18 条**完整标题（含"豆包AI-一键生成PPT"这类推广）
- 哔哩哔哩首页：**13 条**视频标题 + 播放量，
  另有导航、搜索框占位符、广告位

**用户什么都没做，只是开着那个页面，一整页内容就进了上下文。**

#### 这对设计意味着什么

**1. 观察的默认值必须是「最小」，而不是「全部」。**
之前说"截图是最大的成本变量"（§14.1）—— 现在要补一句：
**控件树一样是，而且它更隐蔽**，因为它看起来"结构化、便宜"。
B站那 13 条视频标题对"点开某个视频"这个任务毫无用处，纯是负担和风险。

**2. 需要一层「观察裁剪」，而且它属于框架不属于工具。**
可交互元素（可 Invoke / 有 pattern）优先保留；
纯展示文本按需、按区域、按任务给。
这正是 UFO 的 `control_filter` 在干的事（§14.8），
但我们之前只把它当"省 token"，现在要把它当**隐私边界**。

**3. §14.8 那条「观察边界 ≠ 输入边界」有了实感。**
cc-haha 那句"输入不会落到未授权应用，不能推导出截图不会泄露其他窗口"，
在这里变成了具体数字：**你能读到的，远远超过你要操作的。**

**4. 观察本身要可见、可回放。**
§13.10 说的"把模型当时看到的作为事件进消息流"多了一层意义 ——
用户需要能看到"这一轮智能体到底读了什么"。否则这种泄漏是无声的。

**一个诚实的保留**：微信那个窗口矩形是 `0x0`（当时处于最小化或隐藏状态），
所以它只有 3 个节点这件事**不能完全归因于 MMUI 自绘** ——
需要一个可见状态下的对照才能下结论。

### 14.16 对照实验：VS Code 的树到底能不能打开

这一轮把三个变量逐个试了。**结论和预期不一样，而且很关键。**

#### 三个变量，只有第三个有用

| 条件 | 节点数 | 有内容吗 |
|---|---|---|
| 最小化状态 | 3 | —— （微信，不可比） |
| **微信恢复正常显示** | **2** | **没有** —— 仍是 `MMUIRenderSubWindowHW` 一个空 pane |
| VS Code 普通重启 | 19 | 没有 —— 只有标题 + 四个窗口按钮 |
| VS Code `--force-renderer-accessibility` | **37** | **仍然没有** —— 只多了一个空的 `DocumentControl` |
| **VS Code `editor.accessibilitySupport: "on"`** | **93** | **有了** |

**两个反直觉的点：**

1. **微信的结论现在坐实了。** 恢复正常显示后节点数从 3 变成 2（连标题栏都没了），
   内容依然是零。**MMUI 自绘确实不暴露任何东西** —— 这是第 4 带的干净样本。
2. **那个 flag 根本不是开关。** `--force-renderer-accessibility` 只把节点从 19 提到 37，
   `DocumentControl` 依旧是空的。**真正的开关是 VS Code 自己的
   `editor.accessibilitySupport: "on"`** —— 打开之后菜单
   （File / Edit / Selection / View / Go / Run / Terminal / Help）、
   工具栏、状态栏全都出来了。

#### 一个还没搞清楚的副作用

我在**隔离配置目录**里改了那个设置并重启隔离实例，结果**你原本那个 VS Code
（我从没重启过它）也从 19 个节点变成了 104 个**，而且关掉隔离实例后**保持不退**。

机制我不确定，最可能是：**有 UIA 客户端在查询这件事本身是个系统级信号**，
Chromium/Electron 检测到就按 `auto` 打开了无障碍 —— 而
`editor.accessibilitySupport` 默认正是 `auto`。

**这条如果成立，含义很大**：不需要改任何设置，
**只要你的框架在查控件树，Chromium 系应用就会自己把树建起来。**
但这个推测我没验证，先按"不确定"记着。

#### VS Code 打开之后暴露的到底是什么

这才是最有价值的数据。它给出的状态栏内容是**精确的结构化状态**：

```
C++                    语言
Win32, C/C++ 配置       配置
IntelliSense: 就绪      分析器状态
CRLF                   行尾符
UTF-8                  编码
空格: 4                 缩进
行 72，列 24            光标位置          ← 这个正是设计里要的
没有问题 / 0 / 0        诊断计数
信息: 在工作区的父文件夹或打开的文件中找到了 git 存储库。是否要打开存储库?
```

**§14.2 那张分层表现在被实测验证了** ——
"编辑器层"要的东西（语言、光标、编码、行尾、缩进、诊断）**UIA 全能给，而且是精确的**。

**但它给不了内容**：没有编辑器文本，资源管理器里也只有"资源管理器"这个标签，
没有文件树条目。

> **所以 UIA 和扩展 API 不是二选一，是互补的：**
> **UIA 给你外壳与状态，扩展给你内容。**
> 这正好是 §14.4 那个最小版本的设计 —— 只是现在知道了，
> "状态"那一半可以完全由 UIA 免费提供，不必自己写扩展去取。

#### 代价要提前知道

打开 `editor.accessibilitySupport: "on"` 会**改变 VS Code 的编辑器渲染**
（切到面向屏幕阅读器的 DOM 模式，状态栏会出现 "Screen Reader Optimized"）。
对用户体验是有影响的，而且这是**为了自动化去改用户编辑器**——
在托管场景里必须算进"我们要对用户的环境做什么"。

### 14.17 实测：网页能被读到什么程度

Edge 打开一个网页后重扫：**744 个节点 / 351 个有名字 / 69 个可 Invoke**。
扫的是一个**账户总览页**，结果读到了：

- 可用余额、今日消费、本月消费、总消费、累计充值、冻结金额、赠送金额
- 完整导航结构：组织认证 / 项目管理 / **API Key 管理** / 用量限制 / 文件 /
  账户总览 / 账户充值 / 充值明细 / 计费明细 / 发票管理 / 代金券管理 / 导出记录
- 消费分析：逐月金额、产品消费 Top（Context Caching、模型推理）、
  **模型消费 Top（`kimi-k3`、`kimi-k2.6`）**、项目消费
- 公告横幅（"🎉 Kimi K3 旗舰模型已正式发布"）、未读消息标记

#### 结论一：网页不是"只能拿到可点的元素"，是**整页 DOM 文本**

这是和原生应用最大的区别。VS Code 那个案例里 UIA 只给了外壳和状态栏；
**浏览器把整个 DOM 都交出来了** —— 包括一切纯展示文本。

**没有任何视觉模型参与。** 一页财务数据是纯文本读出来的。

#### 结论二：树给的是 DOM 的结构，不是语义的值

留意余额是怎么出现的 —— 它被拆成了四个独立的 `TextControl`：

```
TextControl  ￥
TextControl  24
TextControl  .
TextControl  63898
```

因为页面就是这么渲染的（每个片段一个 span）。**所以"拍平成一串文本"是错的** ——
你会得到 `￥ 24 . 63898` 这种碎片。

好在层级还在：父节点给出了"可用余额"这个标签，所以**配对是能恢复的**，
但前提是**保留层级关系，而不是拍平**。

> **这条对管线的要求是具体的**：扁平化必须在"语义组"这一层做，
> 不能在最底层做。UFO 的 `flatten_ui_tree()` 之后还要过 `control_filter`，
> 顺序不能反。

#### 结论三：§14.15 那条"观察即泄漏"在这里达到最大值

一个原生应用窗口能给几十到几百个节点，**一个网页能上千**。
而 351 个有名字的节点里，对"点一下某个菜单"这个任务有用的可能只有 5 个。

**而且这次扫的是有钱的页面。** 观察通道默认把整页读进来这件事，
在电商、邮箱、后台、网银这些场景下就是直接的风险 ——
和 §14.8 那条"观察边界 ≠ 输入边界"是同一个问题，只是量级更大。

**所以"观察裁剪"不是优化项，是默认必须存在的层**（§14.15）。

### 14.18 那点风险到底在哪

先把三件性质完全不同的事分开 —— 混在一起谈就会得出"要么无所谓、要么很危险"两个都不对的结论。

#### ① 余额本身：基本无害

本地智能体、本地模型、不出机器的时候，它读你的余额和你自己看余额**没有区别**。
**这一条不需要防御**，把它当事故是反应过度。

#### ② 真正的分界线：「观察」会变成「上传 + 落盘 + 记忆」

| 环节 | 在你的项目里发生在哪 | 后果 |
|---|---|---|
| **出机器** | 云端 API（枢恒 / maskface / EasyTerminal / WXBot 默认都是 DeepSeek） | 进了别人的日志 |
| **落盘** | `chat.jsonl` / `llm.jsonl`（枢恒Ⅵ、EasyTerminal 都有） | 从瞬时变成长期 |
| **进记忆** | §16 那套碎片 / 知识页 / 摘要树 | **从"读到一次"变成"以后反复召回"** |

**第三条是自己设计出来的放大器。** §16 的沉淀机制会把观察变成长期记忆 ——
"这个人余额 ￥24.6" 一旦被语义索引，就会在**无关的会话里被召回**。
它不再是一次泄漏，是**一笔写入**。

#### ③ 更该担心的是另一件事：第三方内容进入了「有手」的上下文

MSN 新闻流、B 站视频标题、广告位 —— 这些**不是用户的秘密，是第三方注入的文本**。
那一页 744 个节点里，大部分是别人写的字。

这不是隐私问题，是**注入**问题：

- 页面可以写指令（"忽略之前的指示…"）；
- 页面可以写"事实"（让智能体以为某件事为真）；
- **而智能体是有手的** —— 它能点、能输入。

**这比余额严重得多**：余额只是被看到，注入是被执行。

#### 顺带一条：观察结果会自己变成新的存放点

§13.10 说要把"模型当时看到了什么"作为事件进消息流、
让 GUI 能回放 —— 那意味着**观察结果被存下来了**。
于是它多了一个被围观、被截屏、被共享的位置。
这不是反对回放，是提醒回放需要和原数据同样的清理策略。

#### 策略应该跟着「数据去哪」走，不是跟着安全洁癖走

| 部署形态 | 观察应该多宽 |
|---|---|
| 本地模型、不出机器 | **可以宽** —— 只是 token 成本问题 |
| 云端 API | **要窄** —— 视野 = 上传量 |
| 还有远程通道 / 微信转发 | **更窄** —— 多了一条转发路径 |

#### 三条具体约束

1. **观察结果分级**：可交互元素（一等）> 用户自己的内容（二等）>
   第三方内容（三等，默认不进）。
2. **从窗口读来的文本永远是「不可信输入」**，不能当指令，必须带来源标注。
   这和 §11.2 的"事实与意义分开"是同一类动作 ——
   **观察说的是"屏幕上写着什么"，不是"事情是什么"。**
3. **沉淀的输入必须是「结论」，不能是「原始观察」**（补进 §16）。
   否则记忆系统会自动把看到的一切变成长期知识。

#### 一个反向的提醒

**裁剪过度会让智能体变笨** —— 它可能正好需要那一行才判断得出下一步。
所以不是"过滤得越狠越好"，而是**按任务裁、并且让裁剪可见、可临时放开**。
这又是 §13.10 那条"观察作为事件进消息流"的用处：
**用户看得见它读了什么，才有机会说"再看仔细点"。**

## 15. 模型拼装与解耦

### 15.1 模型不是一个字符串，是一个组合

| 层 | 组件 | 你现在的状态 |
|---|---|---|
| 提供方适配 | provider adapter | §5.9 已定 |
| 基座模型 | base model | 选型 |
| 适配器 / 微调 | LoRA / fine-tune | 无 |
| 采样参数 | temperature / top_p / reasoning effort / seed | 有 |
| **推理策略** | 单次 / 级联 / 自洽 | **枢恒Ⅵ 的 Logos 已有** |
| 提示词编译 | prompt compiler | §8 |
| **上下文策略** | scrub / compact / pop | **枢恒Ⅵ 已有** |
| 工具绑定 | binding | §2.3 |
| **输出修复** | JSON 修复管线 | **枢恒Ⅵ 的四层修复已有** |
| 守卫 | 输出校验 / 拒答策略 | 无 |

**一个关键认识：枢恒Ⅵ 的 Logos 模式其实已经是一个"拼装出来的模型"**
—— LLM_A（短期意图）+ LLM_B（全局意图）→ LLM_C（统一纲领）级联，
对外表现为一个模型。Overlord 的 Architect / Robot / Reviewer 同理。

**把它们看成"复合模型"，而不是"工作流"，这套拼装就自然了。**
工作流是 harness 编排的步骤；复合模型则是一个**对外有单一身份**的东西 ——
给它一个 prompt，它给回一个结果，内部有几跳是它自己的事。

### 15.2 但因此继承了一个硬约束：拼装必须在绑定时刻凝固

§5.4 定了前缀必须字节稳定。所以拼装不能是随请求随意发生的：

| 变化的东西 | 属于 | 能不能每次变 |
|---|---|---|
| 结构（哪些层、哪个人设、哪些工具） | 绑定 | **不能** |
| 参数（temperature 等） | 请求参数，不进前缀 | 能 |
| 进前缀的那部分提示词 | 绑定 | **不能** |

> 规则：**拼装的结果必须凝固成一个具名、有版本、可寻址的实例。**
> 运行期不存在"半成品模型"。

否则你会同时丢掉三样东西：**缓存**（前缀漂移）、**可复现**（不知道当时用的哪套）、
**可撤销**（权限挂在谁身上？）。

### 15.3 一个实用警告：层次越多，定位越难

输出不对时，问题在基座、采样、人设、提示词编译、上下文策略，还是工具绑定？

解法是 §11.3 那条机制的复用：**每次生成留一份组合清单**
（composition manifest —— 哪些部件、哪个版本）。
和工具 manifest 是同一套办法，可以直接共用生成与校验的设施。

### 15.4 解耦清单

把"解耦"具体化。到目前为止，需要解耦的是这些轴：

## 16. 记忆与持久化：锚点问题

### 16.1 问题可能提错了：不是「窗口取代路径」

先把三种身份分开：

| 身份 | 例子 | 寿命 |
|---|---|---|
| **位置身份** | `D:\proj` | 长，但会漂（移动、重装、换机器、克隆到别处） |
| **会话身份** | 窗口 / 进程 | 短，进程一死就没，而且 hwnd 会被复用 |
| **内容身份** | 文件哈希、符号、git 仓库 | **最长**，位置变了它还在 |

所以正确的说法不是"锚点从路径换成窗口"，而是 ——

> **锚点从「位置」换成「内容」。**
> 窗口不是新锚点，它是**发现锚点的入口**（§14.7 已经走了半步：
> 从 IDE 读出工作区。现在再进一步：连工作区路径都不是最终锚点）。

### 16.2 大眼已经在用的是**内容锚点**

`bigeye-main/memory/file_crystal_store.py`——所谓"金字塔 hash 文件系统"：

```
文件 → 切片 → SHA256 查重 → "三问压缩"（结论 / 为什么 / 下一步）
     → 金字塔多层摘要（原始切片 → 摘要 → 上层摘要）
     → crystal_parent_id 血统链
     → 内容变更检测（hash 变化 → stale）
```

**这直接回答了你这个问题。** 它的锚点是 `SHA256(内容)`，所以：

- **路径变了但内容没变 → 记忆照样命中。** 项目挪个目录、换台机器重新克隆，
  记忆不丢。
- **内容变了 → 标 `stale`，而不是丢弃。** 过期是一个**状态**，不是删除 ——
  于是模型能知道"这里我记过，但可能已经不对了"，而不是一无所知。

同样的取向在另外两层也看得到：摘要树按主题聚合、攒够证据才成文
（新证据 → 重写 `vN+1`，**旧版留档可回溯**）；知识页本身就是版本化知识库。
**都是"内容 + 版本"，不是"位置 + 覆盖"。**

### 16.3 大眼的「沉淀」正好是窗口→项目的那座桥

它还有一层机制叫**叙事沉淀**（`4.6`）：任务结束或记忆整理时，
把碎片用第一人称串成故事存进 `story` 层；`story` 层**每轮常驻 5 条**，
提供"我是谁、我经历过什么"的连续自我。

换个角度看，这就是**解决"窗口是短命锚点"的现成机制**：

> **关窗 / 切项目 / 任务结束时跑一次沉淀，
> 把会话里值得留的东西压到长期层去。**

本质上是**开会记纪要**。会话可以短命，因为它的产出被搬到了长命的地方。

顺带一提它处理上下文截断的方式也值得抄：截断之后会**告诉模型"少了什么、怎么翻"**，
同时写一条 `context_wall` 碎片，`expand_compressed(topic, anchor)` 能取回原文。
**丢失是可检索的，不是无声的。**

### 16.4 语义网络的贡献：记忆的坐标应该是**符号**

你自己那份设计里已经写了那句关键话：

> 代码事实是**可查询、可验证**的（谁调用谁、有几条路径），比聊天记忆更可靠。

这句话在持久化上有一个很强的推论：

**行号是坐标，但它会漂；符号名也漂，但漂得少得多；而且它可以被重新解析。**

所以记忆应该记 `create_student`（符号名路径），而不是 `api.rs:223`（行号）。
这正是 serena 用 `name_path`（`Class/method`）寻址的原因，
也正是 `lsp_symbol_demo` 在做的事 —— **你的语义网络项目已经提供了记忆需要的坐标系。**

由此记忆分成两类，寿命完全不同：

| 类型 | 例子 | 锚点变了会怎样 |
|---|---|---|
| **叙述型** | "我们决定用方案 X" | **不可验证** —— 锚点丢了就丢 |
| **可验证型** | "`create_student` 调用 `gen_id`" | **可重新解析** —— 到新锚点上再验一次就知道还成不成立 |

**可验证的记忆能在锚点迁移后重新落地。** 这是"内容锚点"在代码场景下的具体形态。

### 16.5 三层的锚点分配

把上面的东西合起来，答案是一张表：

| 层 | 存什么 | 寿命 | 锚点 |
|---|---|---|---|
| **会话层** | 思维链、当前工作集、面板布局 | 本次会话 | 会话（窗口可以） |
| **项目层** | 决策、约定、任务模板、DAG 模板 | 项目 | **git 身份**（remote + 仓库结构），退化用规范路径 |
| **文件层** | 文件晶体、切片摘要 | 跟内容 | **内容哈希（SHA256）** |
| **符号层** | 代码事实、注释、结论 | 跟语义 | **符号名路径（可重新解析）** |

> **规则：锚点的粒度必须和记忆的粒度匹配。**

一条文件改一行哈希就变，所以哈希只适合文件级；
项目级记忆用哈希会碎成渣，必须用更粗的锚（git 身份）。
这条如果搞错，就是"记忆永远命中不了"或者"记忆永远过期"。

### 16.6 降级必须显式

锚点不是永远可得，所以要有一条阶梯，按可得性往下退：

```
内容哈希 / 符号
    ↓ 拿不到
git 身份（remote + 仓库根）
    ↓ 没有 git
规范路径（注意：大小写 / symlink / 8.3 短名都要归一）
    ↓ 不是文件类应用
窗口会话（浏览器标签、聊天账号、用户数据目录）
    ↓ 什么都没有
只有进程
```

**每降一级，记忆的寿命就短一截 —— 而这件事必须告诉用户。**
"这次的记忆挂在窗口上，关掉就没了"和"记忆存在这个项目里"是两种完全不同的承诺，
不能都渲染成同一句"已保存"。

失败模式清单（都要显式处理，不能静默）：

| 情况 | 应该发生的 |
|---|---|
| 同名不同路径 | 不能按名字合并 —— 用规范路径 |
| 同项目换路径 | 命中（哈希 / git 身份的价值） |
| 同路径换了项目（删了重克隆） | git remote 一致则命中；否则要问 |
| 临时目录 / 一次性 checkout | **不该污染长期记忆** |
| 窗口重开、项目没变 | 恢复（走锚点，不走窗口） |
| 窗口被复用给另一个项目 | 记忆跟着锚点切，不跟着窗口 |
| 内容变了 | 标 `stale`，不删（大眼做法） |

### 16.7 接进框架

1. **记忆本来就是一个实例**（§3 的清单里有它），分层就是多个实例。
2. **沉淀是一个动作**，由关窗 / 切项目 / 任务结束触发，**走消息流** ——
   于是它可审计、可重放、可被 GUI 显示。
3. **记忆条目也要版本化且可验证**，复用 §11.3 那套机制。
   `stale` 是状态不是删除。
4. **沉淀的输入必须是「结论」，不能是「原始观察」**（见 §14.18）。
   否则观察通道读到的一切都会自动变成长期知识 ——
   一个网页上偶然出现的数字、一段第三方文案，都会被索引进记忆。
   这条和枢恒里"结论写板不写聊天"是同一条纪律。
